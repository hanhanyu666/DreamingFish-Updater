DreamingFish Updater 是一套面向 Minecraft 整合包服务器的自托管更新系统。服主维护一份标准整合包目录，在管理端预览差异并发布；玩家照常使用 PCL、HMCL 等启动器，游戏启动前由玩家端检查并安全更新，完成后继续进入 Minecraft。

它不接管账号、不替换启动器，也不会把玩家电脑粗暴地覆盖成服务器目录。普通内容尊重玩家自己的选择，真正必须一致的内容再由服主明确设置为强制同步。

## 它解决什么问题

传统整合包更新往往意味着重新压缩、重新上传、让玩家手动覆盖，或者要求玩家按顺序安装一串补丁。DreamingFish Updater 把这件事拆成一条更清楚的流程：

1. 服主只维护自己希望发布的文件。
2. 管理端扫描并列出新增、修改和移除，确认以后生成一份带签名的完整目标状态。
3. 玩家启动时只下载自己电脑上真正变化的文件。
4. 下载内容先校验、暂存和备份，全部确认无误以后才替换实例。
5. 更新成功后继续启动 Minecraft；中断或失败时先恢复，不留下半套客户端。

每个发布都是完整目标状态，不是只能接在上一个版本后面的补丁。因此玩家可以从任何带签名基线的正式整合包直接更新到最新版，不必按顺序补齐中间版本。

## 核心能力

| 能力 | 实际效果 |
| --- | --- |
| 差异更新 | 只下载新增或发生变化的对象，大文件支持断点续传和并行下载。 |
| 安全发布 | 项目清单使用 Ed25519 签名，文件使用 SHA-256 与大小校验，公共文件源无法伪造可信版本。 |
| 事务安装 | 先备份、再暂存、最后原子替换；异常退出后读取事务日志恢复原状态。 |
| Web 管理端 | 文件上传、目录树管理、差异预览、发布、回滚、玩家程序和首次部署包都能在网页中处理。 |
| 玩家本地控制 | 普通同步下，玩家可让文件、目录或模组不再受服务器管理，选择只保存在自己的电脑上。 |
| 玩家端自更新 | 更新器程序与整合包内容使用两条独立发布线，程序升级无需重新分发整个客户端。 |
| 个性化界面 | 每个项目都能配置服务器名称、封面、标题、副标题、颜色、公告、新闻、规则和玩法页面。 |
| 离线启动 | 服务器临时离线时，可以复用最近一次已经验证的完整安装；安全错误不会被伪装成普通断网。 |

## 两种同步策略

| 默认同步 | 强制同步 |
| --- | --- |
| 适合大多数模组和配置 | 适合核心模组、关键配置和必须一致的内容 |
| 服务器发布的文件正常更新 | 指定目录或文件必须和服务器保持一致 |
| 玩家额外添加的内容不会被顺手删除 | 范围内冲突内容会先归档，再安全移出实例 |
| 玩家可以在本机调整管理范围或停用非强制模组 | 玩家不能在本机豁免强制目标 |

服主从标准目录移除旧文件时，还可以逐项决定：让玩家端删除，或者只放弃管理并保留玩家已有副本。

## 玩家看到什么

玩家仍然从自己熟悉的 Minecraft 启动器启动游戏。Agent 会拉起 DreamingFish 玩家端，玩家能清楚看到本次检查、下载进度、更新记录和启动状态；检查完成后，Minecraft 照常继续启动。

玩家端同时提供：

- 本次更新、更新记录与运行记录；
- 按目录或单文件管理本地内容；
- 服务器模组与玩家自选模组的独立启停；
- 服主自定义的公告、活动、玩法、规则和世界观页面；
- 与服务器风格一致的名称、封面、强调色和首页介绍。

普通同步下的本地选择不会上传到服务器。

### 玩家轻松更新，服主优雅管理。

梦鱼更新器是为广大 Minecraft 模组服设计的管理工具。开模组服的腐竹们应该都知道：模组出了 Bug，或者服务器崩服需要删改内容时，处理起来有多痛苦。一方面，你要清楚地告诉玩家该如何处理有问题的模组；另一方面，如果服务器有自制模组需要频繁更新，每次都让玩家手动修改，实在让人头疼。你可能还想给自己的服务器设计一个酷炫的启动客户端，在里面展示新闻、公告以及更多内容……因此，我们制作了梦鱼更新器。它是一个更新器，也可以成为你的服务器专属客户端。

梦鱼更新器是一个安全可靠、自主可控、易于部署的 Minecraft 客户端管理工具：服主可以用 Web 或可交互终端管理项目与发布，玩家端在启动前自动更新，玩家自己的模组和文件也始终保有清楚的控制权。

**玩家是来玩服务器的，还是来玩资源管理器的？**

把手动拖模组、反复对版本和担心更新失败的麻烦，交给梦鱼更新器。

服主

##### 用 Web 或终端管理内容与发布

日常操作可以在优雅的 Web 管理页面完成，也可以使用可交互终端整理文件、选择同步策略、发布版本和管理玩家实例。

玩家

##### 启动前自动更新，同时保留控制权

玩家继续使用 PCL、HMCL 等现有启动器；服主需要先按对应启动器完成 Java Agent 接入，梦鱼更新器只在游戏启动前处理更新。

#### 从服主发布，到玩家进入游戏

**Web 管理**添加、删除或更新模组、配置和资源，决定服务器要管理什么。

**选择策略**默认同步尊重玩家本地选择；强制同步守住关键内容边界。

**自动更新**只下载真正变化的内容，完成签名、哈希和安装检查。

**安全启动**更新失败自动恢复；成功后继续进入 Minecraft。

#### 爱咋删，爱咋加，启动就完了。

服主怎么删、怎么加，玩家端都能追到最新目标状态。默认同步下，玩家自己添加的模组和文件不会被误删；玩家还可以手动决定哪些本地内容继续交给更新器管理。

-   服务器内容与玩家自选内容分开识别，互不打架。
-   玩家可以按文件或目录管理本地内容，保留对客户端的控制权。
-   读取 Forge/NeoForge 的 `modId`，识别 Fabric 模组 ID；模组升级或改名后仍能尽量保留选择。
-   玩家端更新器可以独立自更新，与整合包更新渠道分开。

#### 服主有两种同步策略

管理端不把所有玩家电脑粗暴地全盘覆盖，而是让服主按内容的重要程度选择同步边界。

DEFAULT · 默认同步

##### 尊重玩家本地选择

适合大多数内容。服务器发布的内容会保持最新；玩家额外添加的模组和文件保留不动，玩家可在本机豁免非强制内容或停用非强制模组。

-   不主动删除玩家额外内容
-   玩家可以自己管理文件和模组
-   只对发布清单中的内容负责

FORCED · 强制同步

##### 关键内容保持一致

适合核心模组、关键配置和必须一致的文件。开启后，玩家端会强制保持与服务器一致；发生冲突时，玩家自己添加的模组会先安全备份，再移除或替换。

-   可按目录或单个文件开启
-   关键内容始终跟随服务器版本
-   冲突内容可恢复，策略边界清楚

#### 安全更新，不留下半套状态

更新不是“下载完就覆盖”。梦鱼更新器先确认发布可信，再逐项校验，最后以事务方式安装；任何一步失败，都不会把未验证的状态交给玩家启动。

##### 可信发布

管理端用 Ed25519 签名发布清单，玩家先确认项目身份与目标版本。

##### 逐项校验

文件通过 SHA-256 与大小校验，损坏或不匹配的内容不会进入安装。

##### 事务安装

先备份、再暂存、最后原子替换；中断时恢复原状态，不留下半套更新。

##### 快捷回退

发现问题可一键回退到稳定发布，历史发布保持不被改写。

#### 不改你的启动器，也支持主流模组加载器

启动器

##### PCL、HMCL 可以继续用，接入方式不同

梦鱼更新器不接管账号、游戏安装或实例选择。PCL 优先使用专属 `{verpath}` 参数；版本 JSON 的 `arguments.jvm` 可同时兼容 PCL 和 HMCL，分发前应检查实际启动命令。

模组加载器

##### Forge、NeoForge、Fabric 都能识别

通过模组元数据识别组件，帮助玩家保留自己的选择；服务器内容和玩家自选内容各自管理，避免更新时互相影响。

### 下载与首次配置

让我们跟着这篇教程一步步来：下载解压管理端，完成第一次运行时的引导配置，让管理端先跑起来。

#### 一、先认识两个组成部分

开始部署之前，先记住整个系统由两个部分构成：**管理端**和 **玩家端**。管理端可以运行在运行 Minecraft 的服务器上，也可以运行在其他服务器上；玩家端运行在玩家电脑上，由**玩家端本体**和 **Agent（启动引导器）**组成。让我们先认识这两个部分。

服主使用

##### 管理端

安装在服务器上，负责管理内容、发布版本、制作玩家实例，并启动玩家下载服务。

玩家使用

##### 玩家端

随整合包发给玩家的桌面程序，由**玩家端本体**和 **Agent（启动引导器）**组成。本体负责在游戏启动前检查和更新文件；Agent 挂在启动器里，负责拉起玩家端、等待启动许可，并参与玩家端自更新与失败回退。

**一次启动的协作过程：**

**服主发布**在管理端维护标准目录、扫描并发布新版本。

**服主完成启动器接入**按 PCL 或 HMCL 的实际规则配置 Agent，并确认版本隔离生效。

**玩家启动游戏**启动器加载 Agent，Agent 再拉起玩家端。

**返回启动许可**玩家端完成检查后放行，Minecraft 正常加载。

#### 二、准备发行包与三个位置

管理端和玩家端发行包都自带运行环境，不需要额外安装 Java。建议先准备以下三个固定位置：

Windows 目录示例 **[复制]**

```text
D:\管理端       管理端程序与自动生成的数据
D:\被管理的文件      服主希望更新器管理的内容
D:\待发布的完整游戏版本      准备发给玩家的完整 Minecraft 实例
```

-   `D:\管理端` 应长期保留，升级管理端时继续使用其中的 `data` 和设置文件。
-   `D:\被管理的文件` 不要求是完整游戏目录。只管理模组时可以只有 `mods`；只管理配置时也可以只有需要的 `config`。
-   `D:\待发布的完整游戏版本` 是最终交给玩家的完整实例，它由启动器、游戏文件和 DreamingFish 组件共同组成。

#### 三、下载解压管理端

##### 解压到固定目录

Windows 将管理端压缩包解压到 `D:\管理端`；Linux 将管理端压缩包解压到长期使用的目录，例如 `/opt/dfs-admin`。两边都一样：不要每次升级都新建一套空目录。

##### 运行管理端

Windows 双击 `DreamingFishAdmin.exe` 或从 PowerShell 启动；Linux 解压后在发行包根目录运行 `./dfs-admin`，建议用 `tmux` 挂起（如 `tmux new -s dfs ./dfs-admin`），断开 SSH 后管理端仍会继续运行。

#### 四、第一次运行：跟着终端引导走

第一次启动管理端会进入“首次使用引导”。默认值已经适合大多数情况，**不确定就直接按回车**。下面就是你第一次运行时会看到的终端界面（Linux 路径以 `/opt/dfs-admin` 为例，Windows 对应 `D:\管理端`）：

下面会对三步进行讲解。

第 1 步 · 数据保存位置

```text
DreamingFish 整合包更新管理端
================================

首次使用引导
================
欢迎使用 DreamingFish Updater！
请跟随引导完成设置。如果不确定怎么填，直接按回车使用默认值即可。

[1/3] 管理端数据保存位置
管理端会把项目设置、发布记录和签名密钥自动保存在下面这个文件夹：
  /opt/dfs-admin/data
这个 data 文件夹位于管理端根目录中，非常重要，请勿删除！
```

**data 里面会放什么？为什么重要**

项目设置、发布记录、签名密钥和全部内容对象都存在 `data` 里，相当于管理端的“全部家当”。升级或迁移管理端时，把旧版本的 `data` 连同 `management-settings.json` 等设置文件一起搬到新版本根目录，项目和发布历史就会原样恢复；备份时也请优先备份 `data`，不要只复制一个空目录。

第 2 步 · 玩家下载服务

```text
[2/3] 配置玩家下载服务
玩家更新器会通过这项服务下载模组和配置文件。
监听地址：
  0.0.0.0   = 允许其他电脑连接，部署在服务器或 VPS 时使用（推荐）
  127.0.0.1 = 只有当前电脑能连接，仅在内部测试时使用
下载服务监听地址（一般直接按回车） [0.0.0.0]：
下载服务端口（一般直接按回车） [8080]：
```

**这里填的不是公网地址**

这一步配置的是服务器上的监听地址和端口：`0.0.0.0` 表示允许其他电脑连接，`8080` 是默认内网端口。玩家真正访问的公网地址（例如 `http://你的公网IP:端口`）要等创建项目时才填写；如果 `8080` 被其他程序占用，就换一个空闲端口。

第 3 步 · Web 管理页面

```text
[3/3] Web 管理页面
这个页面只给管理员使用，不要提供给玩家。
  默认端口是 18080，通常直接按回车。
  默认只监听 127.0.0.1；需要公网访问时，先通过本机或 SSH 隧道注册账户，
  再在服务设置或 Web 页面显式改为 0.0.0.0，并务必配置 HTTPS 反向代理。
Web 管理端口（一般直接按回车） [18080]：
```

**Web 管理页面只给管理员用**

它默认只监听 `127.0.0.1`，只有管理端本机能打开。远程服务器上想用浏览器管理时，先通过 SSH 隧道访问，不要把 `18080` 直接暴露到公网。不用 Web 也没关系，终端菜单同样能完成所有操作。

第 4 步 · 设置完成，创建第一个项目

```text
首次设置已完成
================
  管理端数据：/opt/dfs-admin/data
  下载服务：0.0.0.0:8080
  Web 管理页面：http://127.0.0.1:18080/
  设置文件：/opt/dfs-admin/management-settings.json

还没有整合包项目。推荐在 Web 管理界面中完成首次创建，
每个必填项都带有用途和示例。
  按 Y 进入 Web 管理界面创建，按 N 使用命令行创建。
是否现在启动 Web 管理界面并创建第一个项目？ [Y/n]：Y
```

##### 两种同步模式

这就是第 2 步里我们让你先不要填写「强制同步一级目录」的原因——管理端有两种同步模式：

默认同步

##### 只维护明确托管的内容

发布清单中的文件缺失或损坏时恢复；不在清单中的玩家额外文件默认保留。玩家可以对普通托管内容设置本地豁免。

-   适合大多数整合包项目
-   保留玩家兼容配置与自选模组
-   文件管理边界清晰、温和

强制同步

##### 强制和远程服务器同步

指定范围内的内容以服务器为准：文件会被强制覆盖，**玩家会无法自己添加模组**，多出来的文件会被移入归档。

-   适合核心模组和关键配置
-   可以按一级目录整体强制，或只强制单个文件
-   设置变化需要重新扫描并发布

强制同步分为**强制同步目录**和**强制同步文件**两种：前者按一级目录整体递归强制，比如把 `mods` 设为强制目录；后者只指定单个文件，比如 `config/server-required.toml`。

**强制同步单个文件和默认同步有什么区别？**

你可能会问这个问题：强制同步单个文件的作用，就是可以防止玩家豁免某个文件。比如核心模组，或者你的服务器可能有一些反作弊模组，你可以用强制同步来防止玩家禁用它。

不过，大部分情况下其实都不需要设置强制同步：默认同步已经适合绝大多数整合包项目，等真正遇到需要锁定的内容（比如核心模组、反作弊）时，再按需开启也不迟。

###### 让启动器加载 Bootstrap Agent

**先确认版本隔离真正生效**

实际游戏目录必须是当前版本目录，例如 `.minecraft/versions/Dreamingfish-Building`。HMCL 的“当前版本独立设置”可能覆盖全局版本隔离；不要只看开关，测试启动后还要确认最终命令中的 `--gameDir` 指向当前版本目录。

**使用 PCL 时，优先在该版本的 JVM 参数中填写下面这行：**

PCL 推荐参数 **[复制]**

```text
-javaagent:"{verpath}.dreamingfish-bootstrap/bootstrap-agent.jar"
```

`{verpath}` 是 PCL 提供的版本目录占位符，启动时会自动变成当前版本的真实路径。它不能用于 HMCL 或其他启动器，也不要改成服主电脑上的绝对路径。

**版本 JSON 的 `arguments.jvm` 是 PCL、HMCL 两者通用的接入方式。**如果希望同一个整合包同时兼容 PCL 和 HMCL，可以使用下面的方法；不要把 `${game_directory}` 直接填进 HMCL 的“Java 虚拟机参数”输入框。

打开 `.minecraft/versions/版本名称/版本名称.json`，找到 `"arguments"` 里面的 `"jvm"` 数组，并在数组开头追加下面这一项：

PCL、HMCL 通用 · arguments.jvm 新增项 **[复制]**

```text
"-javaagent:${game_directory}/.dreamingfish-bootstrap/bootstrap-agent.jar"
```

例如，原文件是：

修改前（示例）

```text
"arguments": {
  "jvm": [
    "-Djava.library.path=${natives_directory}"
  ]
}
```

添加后应变成：

修改后（示例） **[复制]**

```text
"arguments": {
  "jvm": [
    "-javaagent:${game_directory}/.dreamingfish-bootstrap/bootstrap-agent.jar",
```

示例中的原参数只是演示位置；你自己的 `jvm` 数组可能有更多内容，必须全部保留，只新增一行并注意英文逗号。保存后完全退出并重新打开启动器，让它重新读取版本 JSON；不要设置 Windows 全局 `JAVA_TOOL_OPTIONS`。

PCL 用户优先使用前面的 `{verpath}` 参数即可；需要兼容 PCL 和 HMCL 时使用版本 JSON。同一个实例不要同时配置两种方式，否则 Agent 会被加载两次。

**分发前必须检查最终启动命令**

正确结果应包含已经展开的绝对 Agent 路径，而不是字面量 `${game_directory}` 或 `{verpath}`。如果启动器执行了“修复版本”、重新安装 Forge 或重建版本 JSON，请再次确认该条目没有被覆盖。

分发时，你可以直接把整个版本目录发给玩家，也可以用启动器导出整合包再分享。导出整合包时要注意：整合包文件夹里要包含玩家端文件——就是刚拖进去的 `.dreamingfish-bootstrap`（隐藏文件夹，别漏）和 `DreamingFishUpdater`，缺了它们，玩家拿到手也不会有更新器。

###### 两种同步模式

这就是创建项目时建议先留空强制同步设置的原因：终端和 Web 使用完全相同的同步规则。

默认同步

##### 只维护明确托管的内容

发布清单中的文件缺失或损坏时恢复；不在清单中的玩家额外文件默认保留。玩家可以对普通托管内容设置本地豁免。

-   适合大多数整合包项目
-   保留玩家兼容配置与自选模组
-   文件管理边界清晰、温和

强制同步

##### 强制和远程服务器同步

指定范围内的内容以服务器为准：文件会被强制覆盖，**玩家会无法自己添加模组**，多出来的文件会被移入归档。

-   适合核心模组和关键配置
-   可以按一级目录整体强制，或只强制单个文件
-   设置变化需要重新扫描并发布

**强制同步一级目录**会递归管理整个目录，例如 `mods`。目录中的文件不能被玩家豁免，玩家额外放入的文件也会被归档移出；以后新增到该目录的文件会自动属于这个规则。

**强制同步文件**只锁定指定文件，例如 `config/server-required.toml`。它的主要作用是禁止玩家豁免该文件，不会清理同目录的其他文件，以后新增文件也不会自动加入。

**大多数项目不需要强制同步**

默认同步已经适合绝大多数整合包。只有核心模组、反作弊或必须保持一致的配置，才建议按需启用强制同步；规则修改后仍需重新扫描并发布才会生效。

##### 第 4 步 · 扫描并发布

文件准备好后，在主菜单选择 `[4] 扫描并发布整合包`。终端会显示与 Web 相同的变更预览：托管文件数、总大小、变更数量、预计下载量、同步范围以及每个新增、修改或移除的文件。

重点检查**移除后的处理**。普通托管文件可以选择“从玩家端删除”，或者“只放弃管理并保留玩家本地文件”；强制同步目录中的文件只能随发布从玩家端移除。第一次发布通常全部是“新增”，基本不会出现这一步。

预览确认无误后，填写本次显示版本（例如 `1.0.0`）、最低玩家端程序版本和更新记录。发布内容是不可变的：如果发现错误，请修正整合包文件目录后再发布一个新版本，不要修改旧版本。

##### 第 5 步 · 制作玩家端（发布玩家端程序）

整合包文件发布完成后，第一次还需要发布玩家端程序。这个过程会把整合包数据、玩家端个性化设置、公网地址和网络传输公钥一起准备好；签名私钥始终留在管理端数据目录，不会进入玩家部署包。

玩家端程序和整合包版本是**两条独立的发布线**：以后只更新模组或配置时，重新发布整合包即可，不需要再次发布玩家端程序；只有更新器程序本身升级时，才需要重新执行 `[6]`。

在主菜单选择 `[6] 发布玩家端程序`，依次完成下面四项：

1.  选择和玩家电脑一致的**平台**，Windows 通常保持 `windows-x64`。
2.  填写玩家端发行包**解压后的根目录**。管理端会自动定位版本目录和 `DreamingFishUpdater.exe`，不要填写 ZIP 文件、`app`、`runtime` 或具体版本子目录。
3.  填写**最低启动引导器版本**，当前通常保持 `0.1.2`；只有重新分发了更高版本 Bootstrap Agent 时才提高。
4.  核对后输入 `Y`，管理端会自动读取程序版本、定位 app-image、生成清单并签名。

接下来，让启动器加载 Bootstrap Agent。**使用 PCL 时，优先在该版本设置的「JVM 参数」（Java 虚拟机参数）中填写：**

PCL 推荐参数 **[复制]**

```text
-javaagent:"{verpath}.dreamingfish-bootstrap/bootstrap-agent.jar"
```

`{verpath}` 是 PCL 专属占位符，启动时会自动替换成当前版本目录。HMCL 和其他启动器不能使用它。

**版本 JSON 的 `arguments.jvm` 是 PCL、HMCL 两者通用的接入方式。**需要让同一个整合包兼容两种启动器时，打开 `.minecraft/versions/版本名称/版本名称.json`，找到 `"arguments"` 中已有的 `"jvm"` 数组，在数组开头追加：

PCL、HMCL 通用 · arguments.jvm 新增项 **[复制]**

```text
"-javaagent:${game_directory}/.dreamingfish-bootstrap/bootstrap-agent.jar"
```

例如原来是：

修改前（示例）

```text
"arguments": {
  "jvm": [
    "-Djava.library.path=${natives_directory}"
  ]
}
```

添加后是：

修改后（示例） **[复制]**

```text
"arguments": {
  "jvm": [
    "-javaagent:${game_directory}/.dreamingfish-bootstrap/bootstrap-agent.jar",
    "-Djava.library.path=${natives_directory}"
  ]
}
```

你自己的原有 JVM 参数必须全部保留，只新增一行并注意英文逗号。保存后完全退出并重新打开启动器；不要把 `${game_directory}` 直接填进 HMCL 的 JVM 参数框。PCL 用户优先使用前面的 `{verpath}`；同一个实例不要再同时配置两种方式。

**分发前检查一次实际启动命令**

确认 `--gameDir` 指向当前版本隔离目录，并且 `-javaagent` 后面已经是实际路径，而不是未替换的 `{verpath}` 或 `${game_directory}`。

分发时，你可以直接把整个版本目录发给玩家，也可以用启动器导出整合包再分享。导出整合包时要注意：整合包文件夹里要包含玩家端文件——就是刚拖进去的 `.dreamingfish-bootstrap`（隐藏文件夹，别漏）和 `DreamingFishUpdater`，缺了它们，玩家拿到手也不会有更新器。

### 日常维护

恭喜你完成了配置！日常维护其实很轻松：改文件、扫描、发布；需要时回滚、备份、升级，一件件来就好。

#### 日常更新客户端流程

日常更新其实就三件事：**给客户端加东西**、**从客户端删东西**，或者**放弃管理某个文件**。不管哪一件，改完「整合包文件目录」后重新扫描并发布，玩家下次启动时就会自动跟上。

##### 为客户端增加文件

想给玩家加新模组、新配置？跟着这几步走：

1.  把文件放进「整合包文件目录」里对应的位置——如果有新模组就放进 `mods`，如果有新配置就放进 `config`。
2.  重新扫描：Web「管理文件」页点「↻ 扫描整合包目录」，或终端选 `[4]` 扫描并发布。
3.  在变更预览里确认新文件都出现了，填好本次显示版本和更新记录，发布。

发布后，玩家下次启动时更新器就会下载这些新文件、放进对应位置——不用玩家手动做任何事。

##### 为客户端删除文件

想从玩家客户端移除某个文件或模组？把文件从「整合包文件目录」里删掉，重新扫描。如果扫描发现源目录里有文件被移除了，管理端会问你这个文件在玩家端怎么处理：

1.  **从玩家端删除**：玩家下次启动时，这个文件会被清理掉。
2.  **只放弃管理，保留玩家本地文件**：服务器不再管理这个文件，玩家电脑上已有的副本原样保留，可以继续使用。

**什么时候选放弃管理？**

当你只是“不想再更新这个文件”、而不是“玩家必须删掉它”的时候。比如某个模组不再维护了，但玩家留着玩没影响——选放弃管理，玩家就能保留它，服务器也不再推送更新。注意两点：放弃管理是对所有玩家生效的，和玩家在自己电脑上单独豁免文件不是一回事；另外强制同步目录或强制同步文件里的内容只能删除，不能放弃管理。

**发布是不可变的**

内容有误就修正目录再发新版本，不要修改旧版本；也可以在网页端快捷回滚，把某个历史版本作为新版本重新发布。玩家端会自动发现并升级到最新版本，低于最低玩家端程序版本的玩家端会先更新程序再更新整合包。

##### 更新玩家端程序

玩家端程序是另一条独立的发布线，和整合包内容互不影响：平时更新模组、改配置，只重新发布整合包就好。而玩家端程序是**可以自更新的**——想给玩家推送新闻、更换更新器背景，或者调整其它个性化内容时，发布一个新版本的玩家端程序就好；玩家端下次启动会自动检查并安装，**不用再把客户端重新发给玩家**。

真正需要重新分发玩家端的情况只有一种：Bootstrap Agent 更新了。Agent 挂在启动器里、由启动器在游戏加载前先拉起，没法像玩家端那样自更新；而 Agent 一般不会更新，除非有重大 Bug——所以绝大多数情况下，玩家端程序都能自己追上最新版。

发布新玩家端程序和第一次完全一样：Web「玩家端程序」页选好平台、填最低 Bootstrap Agent 版本、选玩家端发行包解压后的根目录，点「发布玩家端」；终端选 `[6]`。玩家端程序更新拥有独立的签名清单，安装失败时会回退到上一个已验证版本，不会和整合包内容混在一起。发布整合包时如果填的最低玩家端程序版本高于玩家当前版本，玩家端会先更新程序、再更新整合包。完整的首次发布流程见[「创建第一个项目」](https://dreamingfish-studio.github.io/DreamingFish-Updater-Website/docs/create-project.html)第 5 步。

#### 备份与恢复

如果你特别看重安全性，可以给管理端做加密备份——它包含项目数据、发布记录和签名私钥，跨机器迁移或保护重要环境时用得上（终端专属，Web 不提供）。日常维护不做备份也没有关系。创建备份：

创建加密备份 **[复制]**

```text
dfs-admin backup create --output D:\备份\dreamingfish-20260802.dfb
```

密码从环境变量 `DFS_BACKUP_PASSWORD` 读取；未设置时会在终端中交互式输入并确认。恢复备份：

恢复加密备份 **[复制]**

```text
dfs-admin backup restore D:\备份\dreamingfish-20260802.dfb --force
```

**不要只复制数据库文件或只导出私钥**

备份要整个做、整个恢复。`--force` 会替换现有的管理数据目录，恢复前请确认没有重要新数据。

#### 升级管理端

1.  下载新版管理端并解压。
2.  把旧版根目录中的 `data` 文件夹、`management-settings.json` 和 `management-web-auth.json`（如果注册过 Web 账户）移动或复制到新版根目录。
3.  启动新版管理端，程序会自动读取原有数据。

#### 多项目维护

一个管理端可以维护多个整合包项目。终端操作前会先列出项目让你选择，直接回车使用带 `*` 的默认项目；每个项目拥有独立的显示信息、公共地址、发布历史和签名身份，**不同项目的玩家实例不要混用绑定文件**（详见[「创建第一个项目」](https://dreamingfish-studio.github.io/DreamingFish-Updater-Website/docs/create-project.html)）。

### 常见问题

集中回答 VPS 管理、玩家自选内容、Web 常驻与玩家端程序删除等常见疑问。

#### 管理端在 VPS 上，如何打开 Web 页面？

先在 VPS 的交互终端启动 Web 管理界面，再从自己的电脑建立 SSH 隧道：

SSH 隧道 **[复制]**

```text
ssh -N -L 18080:127.0.0.1:18080 用户名@您的服务器地址
```

保持终端运行，并在自己电脑打开 `http://127.0.0.1:18080/`。

#### 玩家自己添加的模组会被删除吗？

默认同步下会保留并提示。只有当 `mods` 被服主设为强制同步目录时，额外模组才会被移出实例，并进入玩家归档。

#### 标准整合包目录必须是一份完整游戏吗？

不需要。它只需要包含服主希望由更新器管理的目录和文件。游戏本体、存档、日志和启动器通常不应放入标准目录。

#### Web 管理页面必须一直开着吗？

不必须。Web 页面适合管理操作。准备长期只运行玩家下载服务时，可以停止 Web 并在交互主菜单中单独选择 `[9] 启动 HTTP 文件服务`。

#### 玩家端发布后可以删除吗？

可以删除。已发布的玩家端程序版本可以从历史中移除，不影响整合包发布。

#### 为什么三个版本号不同

三个组件生命周期不同。玩家端界面变化不要求管理端同步升级；管理端发布能力变化也不一定需要更新 Agent。独立版本能让升级范围更小，也避免把模组内容版本与更新器程序版本混淆。

## 启动器与加载器

- PCL 与 HMCL 均可接入；PCL 优先使用版本目录参数，两者也可以使用版本 JSON 的 `arguments.jvm` 方式。
- Forge、NeoForge 与 Fabric 模组均可读取元数据，用来识别组件并保留玩家选择。
- DreamingFish Updater 不接管正版登录、游戏下载、Java 选择或实例隔离，这些仍由原启动器负责。

启动器参数容易因为实例隔离方式不同而填错，分发前请按[启动器接入教程](https://dreamingfish-studio.github.io/DreamingFish-Updater-Website/docs/create-project.html#web-step-5)检查最终 Java 启动命令，不要只看设置框里的原始文字。

## 安全边界

- 发布清单经过 Ed25519 签名，玩家实例预先绑定项目公钥。
- 每个文件对象都校验 SHA-256、声明大小与续传响应范围。
- 路径会拒绝绝对路径、`..`、Windows 保留名、大小写冲突和符号链接穿越。
- 同一实例只允许一个更新任务；Minecraft 使用实例时不提交更新或恢复事务。
- 公共文件服务可以使用 HTTP，因为内容真实性由签名与哈希独立保证；正式公网部署仍建议使用 HTTPS 保护访问地址和网络隐私。
- Web 管理页面包含管理能力，不应直接以无密码的 HTTP 暴露到公网。

## 项目组成

| 模块 | 用途 |
| --- | --- |
| `management-cli` | 交互终端、Web 管理界面、账户与服务控制 |
| `management-core` | 项目、扫描、对象库、签名发布、回滚、备份与玩家实例 |
| `bootstrap-agent` | Java 8 字节码的启动引导器，拉起玩家端并等待启动许可 |
| `player-ui` | Tauri + Vue 玩家窗口、个性化页面与本地管理界面 |
| `player-app` | Java 21 更新侧车、日志、本地状态与启动许可控制 |
| `update-engine` | 清单验证、差异下载、事务安装、恢复与玩家端自更新 |
| `protocol` | 项目绑定、发布清单、路径安全、SHA-256 与 Ed25519 |

## 从源码构建

开发环境需要完整 JDK 21、Node.js、Rust 与 Tauri 的 Windows 构建依赖。仓库自带 Maven Wrapper，Maven 缓存默认限制在项目目录。

```powershell
.\mvnw.cmd test

Set-Location .\player-ui
npm test -- --run
cargo test --manifest-path .\src-tauri\Cargo.toml
Set-Location ..

.\packaging\build-distributions.ps1 `
  -Version 0.1.28 `
  -AdminVersion 0.1.18 `
  -TauriPlayer `
  -SkipTests

.\packaging\smoke-test-distributions.ps1 `
  -Version 0.1.28 `
  -AdminVersion 0.1.18
```

发行包烟雾测试会重新解压真实 ZIP，模拟历史发布、签名验证、篡改拒绝、首次部署包与 HTTP 下载服务；测试数据位于 `target/`，成功后自动清理，不会接触现有 Minecraft 实例。
