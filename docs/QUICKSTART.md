# DreamingFish Update System 最简使用教程

这份教程只讲如何把系统跑起来。高级命令、远程中转、备份和故障处理先不用看。

## 先记住四句话

1. 标准整合包目录里放什么，管理端就管理什么；不要求同时存在 `mods` 和 `config`。
2. “发布玩家端程序”只在更新器程序升级时做，不是每次更新模组都做。
3. “制作玩家实例”只在服主要重新发布一个完整整合包下载文件时做，不是每个玩家都做。
4. 玩家只需要安装服主制作好的整合包，然后正常点击 PCL 的“启动游戏”。

## 你需要准备三个位置

下面只是示例路径，可以换成自己的路径：

```text
D:\DFSAdmin       管理端程序
D:\DFSSource      服主要发布的文件
D:\MyModpack      准备发给玩家的完整 Minecraft 实例
```

`D:\DFSSource` 不需要是完整游戏目录。你只想管理模组，就只放：

```text
D:\DFSSource\
    mods\
```

你只想管理配置，就只放：

```text
D:\DFSSource\
    config\
```

管理端只会创建 `D:\DFSSource` 这个根目录，不会强制创建里面的 `mods` 或 `config`。

## 第一次部署

### 第一步：启动管理端

把 `dfs-admin-windows-x64-0.1.8.zip` 解压到：

```text
D:\DFSAdmin
```

双击：

```text
D:\DFSAdmin\dfs-admin.cmd
```

第一次运行时：

- HTTP 监听地址：直接回车；
- HTTP 监听端口：直接回车；
- 是否创建第一个项目：输入 `Y`。

创建项目时可以这样填写：

| 提示 | 示例 |
| --- | --- |
| 项目 ID | `building` |
| 项目显示名称 | `梦鱼建筑服` |
| 标准整合包目录 | `D:\DFSSource` |
| 强制同步一级目录 | 第一次建议直接回车 |
| 玩家访问的公共 HTTP 地址 | `http://你的公网IP:8080` |
| 其它界面选项 | 不确定就直接回车 |

项目创建后，把真正想管理的目录和文件放进 `D:\DFSSource`。

### 第二步：导入玩家端更新器

这一步在玩家端 `0.1.12` 期间只做一次。以后只更新模组或配置时，不需要再做。

把 `dreamingfish-player-windows-x64-0.1.12.zip` 解压到任意临时目录，例如：

```text
D:\DFSPlayerTemplate
```

在管理端主菜单选择：

```text
[6] 发布玩家端程序
```

填写：

| 提示 | 填写 |
| --- | --- |
| 平台 | `windows-x64` |
| 玩家端程序版本 | `0.1.12` |
| 玩家端完整 app-image 目录 | `D:\DFSPlayerTemplate\DreamingFishUpdater\app\0.1.12` |
| 启动程序路径 | `DreamingFishUpdater.exe` |
| 最低启动引导器版本 | `0.1.2` |

确认发布即可。

### 第三步：发布第一个整合包版本

在管理端选择：

```text
[4] 扫描并发布整合包
```

第一次可以填写：

```text
显示版本：1.0.0
最低玩家端程序版本：0.1.12
更新记录：首次发布
确认发布：Y
```

发布前看一眼新增、修改和删除列表。内容不对就取消，不要勉强发布。

管理端会在确认前回显“实际将保存的更新记录”。如果远程 Windows
终端把中文显示成 `P`、`0` 或乱码，必须取消发布。先建立 UTF-8 文本文件，
例如 `D:\更新记录.txt`，然后在更新记录提示中输入：

```text
@D:\更新记录.txt
```

管理端会按 UTF-8 读取文件并再次回显，确认中文完全正确后再输入 `Y`。

### 第四步：制作要发给玩家的完整整合包

先准备好完整 Minecraft 实例，例如：

```text
D:\MyModpack
```

把 `dreamingfish-player-windows-x64-0.1.12.zip` 里的全部内容复制进这个实例根目录。隐藏目录 `.dreamingfish-bootstrap` 也必须复制。

然后在管理端选择：

```text
[7] 制作玩家实例
```

填写：

| 提示 | 填写 |
| --- | --- |
| Minecraft 实例目录 | `D:\MyModpack` |
| 平台 | `windows-x64` |
| 实例内玩家端目录 | 直接回车 |
| 下载包对应版本 | 选择刚发布的 `1.0.0` |

管理端会自动写入服务器身份、签名和这个整合包版本的基线。玩家不需要自己执行这一步。

### 第五步：给 PCL 配置一次启动参数

在 PCL 中打开这个具体版本的设置，把下面一条加入该版本的 JVM 参数：

```text
-javaagent:"{verpath}.dreamingfish-bootstrap/bootstrap-agent.jar"
```

必须保留 `{verpath}`，不要改成你电脑上的绝对路径。

这是服主制作整合包模板时配置一次。导出整合包后，应确认 PCL 的该版本设置也被带入，玩家不应该再手动填写。

### 第六步：启动更新服务

在管理端选择：

```text
[9] 启动 HTTP 文件服务
```

这个窗口需要保持运行。玩家电脑必须能打开：

```text
http://你的公网IP:8080/healthz
```

正常会看到：

```json
{"status":"ok"}
```

最后用 PCL 测试一次 `D:\MyModpack`，确认更新器出现、Minecraft 获得启动许可，再导出并发布整合包。

## 以后更新模组或配置

普通在线更新只有两步：

1. 修改 `D:\DFSSource` 中的文件；
2. 管理端选择 `[4] 扫描并发布整合包`。

不需要再次发布玩家端程序，不需要再次制作玩家实例，也不需要让玩家重新下载完整整合包。玩家下次启动游戏时会自动更新。

## 什么时候才需要重新制作玩家实例

只有当你准备重新上传一个新的“完整整合包下载文件”时，才需要：

1. 把玩家端模板放进新的完整实例；
2. 管理端选择 `[7] 制作玩家实例`；
3. 选择这个下载包实际对应的发布版本；
4. 测试后导出整合包。

例如网站同时保留 1.1、1.2、1.3 三个完整下载包，那么每个包制作时都应带上自己版本的签名基线。玩家即使下载旧的 1.1，也可以在第一次启动时直接更新到最新版本。

## 为什么玩家端看起来经过管理端两次

这两个步骤用途不同：

| 操作 | 实际作用 | 多久做一次 |
| --- | --- | --- |
| `[6] 发布玩家端程序` | 让管理端保存并签名更新器程序，使更新器可以自动升级 | 更新器版本变化时 |
| `[7] 制作玩家实例` | 把具体服务器身份和具体整合包版本写进下载包 | 每次制作新的完整下载包时 |

这些都是服主操作。普通玩家两步都不需要做。

## 强制同步先不要开

第一次使用时，建议“强制同步一级目录”直接留空。这样玩家额外添加的模组只会收到提醒，不会被移走。

等普通更新流程完全跑通以后，再在菜单 `[3] 修改项目设置` 中单独给 `mods` 等目录开启强制同步。

遇到端口、防火墙、远程服务器、备份或错误提示时，再查看 [完整部署参考](./DEPLOYMENT.md)。
