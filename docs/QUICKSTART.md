# DreamingFish Update System 最简使用教程

这份教程用 Web 管理界面完成日常操作。加密备份、自动化命令和故障处理请看
[完整部署参考](./DEPLOYMENT.md)。

## 先记住五句话

1. 标准整合包目录里放什么，管理端就管理什么；不要求同时存在 `mods` 和 `config`。
2. 玩家端程序只在更新器自身升级时发布，不是每次更新模组都发布。
3. 玩家实例只在制作新的完整整合包下载文件时准备，不是每次在线更新都准备。
4. 公共下载服务默认是 `0.0.0.0:8080`，Web 管理页面默认是 `127.0.0.1:18080`，两者使用不同端口，可在服务设置中调整。
5. 玩家只需安装服主做好的整合包，然后正常点击 PCL 的“启动游戏”。

## 准备三个目录

路径可以自行修改：

```text
D:\DFSAdmin       管理端程序和自动生成的 data
D:\DFSSource      服主希望更新器管理的文件
D:\MyModpack      服主电脑上准备发给玩家的完整 Minecraft 实例
```

`D:\DFSSource` 不需要是完整游戏目录。只管理模组时只放：

```text
D:\DFSSource\
    mods\
```

只管理部分配置时也可以只放：

```text
D:\DFSSource\
    config\
        某个模组的配置目录\
```

管理端不会自行创建 `mods` 或 `config`，也不会管理标准目录之外的玩家文件。

## 第一次部署

### 1. 启动管理端和 Web 页面

把 `dfs-admin-windows-x64-0.2.0.zip` 解压到 `D:\DFSAdmin`，双击：

```text
D:\DFSAdmin\DreamingFishAdmin.exe
```

第一次运行时：

- HTTP 监听地址直接回车，使用 `0.0.0.0`；
- HTTP 监听端口直接回车，使用 `8080`；
- 询问是否立刻创建项目时可以输入 `N`，稍后在 Web 页面创建。

进入主菜单后选择：

```text
[10] 启动 Web 管理界面
```

管理端位于当前电脑时，在浏览器打开：

```text
http://127.0.0.1:18080/
```

管理端位于远程服务器时，先在自己的电脑建立 SSH 隧道：

```powershell
ssh -N -L 18080:127.0.0.1:18080 用户名@您的服务器地址
```

SSH 使用非默认端口时再加 `-p <SSH端口>`。保持这个终端运行，然后仍然在自己电脑打开：

```text
http://127.0.0.1:18080/
```

首次打开时创建管理员账户；勾选本机免登录后，通过回环地址访问可以免登录。远程维护使用 SSH 隧道，或用 Caddy/Nginx 把 HTTPS 代理到本机管理端。按 `Ctrl+C` 会停止 Web 管理界面并返回管理端主菜单。

### 2. 创建项目

在 Web 首页点击“新建项目”，填写：

| 字段 | 示例 |
| --- | --- |
| 项目 ID | `building` |
| 项目显示名称 | `我的模组服` |
| 要管理的文件目录 | `D:\DFSSource` |
| 玩家端更新器访问地址 | `http://你的公网IP:8080` |
| Minecraft 服务器地址（可选） | 你的游戏服务器地址 |

公共地址必须能从玩家电脑访问，不能填写 `127.0.0.1`、`localhost` 或
`0.0.0.0`。如果云平台把公网 `39988` 映射到服务器内网 `8080`，这里应填写：

```text
http://你的公网IP:39988
```

创建完成后，把实际要管理的目录和文件放入 `D:\DFSSource`。

### 3. 发布一次玩家端程序

打开“玩家端程序”，选择 `dreamingfish-player-windows-x64-0.2.0.zip`，点击“上传并检查发行包”。核对自动识别的 `0.2.0` 和 `windows-x64`，再点“确认发布玩家端”。最低 Bootstrap Agent 版本位于高级兼容设置，当前保持 `0.1.2`。

发行包已经解压在服务器上时，可展开“从服务器目录发布”，选择解压根目录；管理端会自动定位程序版本目录。以后只更新模组或配置时，不需要重复发布玩家端程序。

### 4. 发布第一个整合包版本

进入“检查并发布”，先点击“↻ 检查整合包内容”。检查文件和规则变化无误后填写：

```text
显示版本：1.0.0
最低玩家端程序版本：0.2.0（高级兼容设置默认自动计算）
更新记录：首次发布
```

点击“发布整合包”，再次确认。Web 页面按 UTF-8 传输中文，不需要使用
`@更新记录.txt` 的终端兼容写法。

如果公共下载服务已经由当前 Web 管理进程启动，发布完成后会自动重启该服务，
页面会明确显示结果；玩家随后访问 `latest` 时会直接取得新版本。

发布是不可变的。内容有误时不要修改旧发布，应修正标准目录后再发布一个新版本。

### 5. 生成首次部署包并合并到本地实例

这一步不要求远程管理服务器拥有完整 Minecraft 实例。进入 Web 左侧“玩家实例”，
使用上方的“生成首次部署包”，填写：

| 字段 | 填写 |
| --- | --- |
| 平台 | `windows-x64` |
| 原整合包对应版本 | 选择刚发布的 `1.0.0` |

点击“下载部署 ZIP”，解压后包含更新器程序、Agent、项目绑定、项目封面和 `1.0.0` 的签名基线。需要把部署包写到管理服务器时，填写输出父目录（例如 `D:\DFSOutput`），再点“写入服务器目录”。

把部署包目录内的全部内容合并到
`D:\MyModpack`。隐藏目录 `.dreamingfish-bootstrap` 不能漏掉。普通玩家不执行
此步骤，他们拿到的应该是已经合并完成的整合包。

如果管理端能直接访问 `D:\MyModpack`，也可以使用同页下方的“制作玩家实例”。
它会直接写入绑定、补齐所选发布文件并生成基线；两种方式二选一即可。

### 6. 给 PCL 写入启动参数

在 PCL 中打开这个具体版本的设置，把下面一条加入该版本的 JVM 参数：

```text
-javaagent:"{verpath}.dreamingfish-bootstrap/bootstrap-agent.jar"
```

必须保留 `{verpath}`，不要改成当前电脑的绝对路径。导出整合包后，确认
PCL 的版本设置也被带入，玩家不应该再手动填写。

### 7. 启动公共下载服务

回到 Web 首页，点击“启动下载服务”。终端和 Web 管理进程需要保持运行。

先在管理服务器访问：

```text
http://127.0.0.1:8080/healthz
```

再从另一台电脑访问：

```text
http://你的公网IP:8080/healthz
```

正常会看到：

```json
{"status":"ok"}
```

最后用 PCL 启动一次 `D:\MyModpack`，确认更新器出现、Minecraft 获得启动
许可，再导出并发布完整整合包。

玩家端无法连接更新服务器时，有完整可信基线且本地安装有效即可离线启动。缺少签名基线会阻断，需要重新制作或修复首次部署包。已有基线但托管内容变化时，玩家可明确选择保留变化继续启动，该结果不会记为验证通过。签名、危险路径或未完成事务错误不适用这个操作。

## 以后更新模组或配置

普通在线更新只做三件事：

1. 修改 `D:\DFSSource` 中的文件；
2. 在“检查并发布”中检查文件和规则变化；
3. 填写新显示版本和更新记录后发布。

不需要再次发布玩家端程序，不需要再次制作玩家实例，也不需要让玩家重新下载
完整整合包。玩家下次启动游戏时会按文件差异更新，只下载本机缺少或内容变化的对象。

也可以直接在 Web“管理内容”页的“整合包文件”中管理 `D:\DFSSource`：从自己当前电脑拖入或
多选上传文件，或切换“从服务器导入”选择服务器已有文件。先暂存并检查清单，确认保存路径、模组版本和替换方式，再确认导入。旧文件归档随管理端 `data/` 保存。

文件列表下方的“操作记录”可查询并撤销导入、替换、移除和设置修改。误改维护规则时，点击“恢复版本设置…”，检查逐项变化后恢复当前已发布版本的维护设置。它不会替换源文件；需要恢复文件时撤销对应文件操作。已经发布过的变化，恢复后还要检查并发布。

检查结果中的移除默认采用“移除玩家副本”：玩家的对应副本先备份再移出，即使停用、自行管理或首次提供也会处理，以后装回仍会处理。

想交给玩家自行决定时，改选“停止维护，留给玩家”。重新把同一资源放回标准目录并发布，会结束普通持续移除；历史坏版本仍须在问题处理中明确结束。

## 什么时候重新制作完整玩家包

只有准备上传新的“完整整合包下载文件”时，才需要：

1. 在“玩家实例”中生成薄首次部署包，并选择该下载包实际对应的发布版本；
2. 下载后合并到本地完整实例；
3. 测试后导出整合包。

网站可以同时保留 1.1、1.2、1.3 等旧完整包。只要每个包制作时绑定了自己的
签名发布基线，玩家下载旧包后也能直接更新到当前最新发布，旧官方文件不会被误判成玩家自选文件。

## 日常只选三种方式

网页的文件管理、上传与版本发放操作见 [管理端工作区](ADMIN-WORKSPACE.md)。在当前目录添加文件后，先暂存检查清单，再确认导入；导入、维护方式和文件移除仍需在“检查并发布”发布后到达玩家。玩家端程序可直接上传发行 ZIP，确认识别结果后再签名发布。

默认使用普通同步，玩家可以停用模组或自行管理。核心模组和必须一致的文件设为强制同步；个人设置设为首次提供，提供后修改、删除或模板更新都不再自动改动，玩家可以主动恢复默认。

选择文件夹强制同步时，发布内容保持一致、额外文件移入玩家备份。范围内不能再设置普通同步、首次提供或可选内容。希望玩家使用自选模组时，让 `mods` 保持普通，再单独强制核心文件。

普通同步内容可以组成可选包，设置默认是否安装，让玩家整组开关。

发现旧版本有问题时，打开“管理内容 → 历史文件与问题处理 → 按发布版本管理”，选择当时的整合包发布，再点击文件旁的“处理这个版本”，填写原因并选择移出或替换。也可以直接使用“处理问题文件”筛选历史版本。替换前先在文件列表准备正确文件。一次检查并发布即可生效；不需要先把已经停止维护的文件重新变成托管。例如 B 之前选择了“停止维护，留给玩家”，后来 B 1.0 出现严重问题，仍可从历史发布选中 B 1.0，要求玩家移出。

首次升级旧项目后请重新检查预览。旧发布的实际删除会迁移为待发布持续要求，普通移除不再逐条显示为问题卡片；如果希望玩家保留，在历史发布找到该文件，展开“移除要求”并选择“允许玩家保留”，再检查并发布。强制同步文件夹仍会处理范围内的额外文件。旧版默认配置设置统一改为首次提供。发布新规则前，应先发布 0.2.0 玩家端程序，否则旧玩家端会拒绝新目标。

## 不想常驻 Web 页面

Web 页面没有定时轮询，空闲资源占用很低。仍想只使用终端时，可以按
`Ctrl+C` 返回主菜单，再选择：

```text
[9] 启动 HTTP 文件服务
```

按 `Ctrl+C` 同样只停止当前 HTTP 服务并返回主菜单。中文交互终端提供主要创建、发布和分发流程；维护规则和操作记录也可用参数式命令管理。加密备份与恢复在 CLI 中提供。

## 升级管理端

停止服务并退出旧管理端，先备份 `data/`、`management-settings.json` 和 `management-web-auth.json`，再用
新 ZIP 中的程序文件覆盖旧目录。若必须换到新目录，把旧 `data/` 放在新
`DreamingFishAdmin.exe` 同级；即使 `management-settings.json` 仍记录旧绝对路径，
新版也会检测有效的本地 `data/management.db` 并自动修正。不要把空 `data/`
误当成备份，也不要把管理端 `data/` 发给玩家。

CLI 加密备份包含项目身份、数据库、签名发布和对象，管理端运行设置、Web 账户和标准目录的未发布文件需要另行保存。本次管理端与玩家端为 0.2.0；发布新版玩家端后，已有玩家可通过签名自更新取得程序，不能覆盖已经发布过的同一程序版本。
