# 玩家端自动升级与自定义更新目录实施计划

编写日期：2026 年 11 月 1 日

本计划安排两项功能：让服主批准官方玩家端程序的新版本，以及把文件更新范围扩展到整合包外层的指定文件。两项功能分别交付，先完成程序升级与服主控制，再交付目录扩展和启动器配置适配。

本计划已随 v0.3.2（管理端 / 桌面 0.3.2、玩家端 0.3.3）发布。下文保留设计目标，实际交付行为以[程序更新说明](PLAYER-PROGRAM-UPDATES.md)、[目录与配置合并](CONTENT-ROOTS.md)和[验证记录](reviews/2026-11-01-implementation-verification.md)为准。

本版按需检查官方目录并缓存 6 小时；服主打开自动发布后，运行中的管理服务每小时检查一次。任务取消沿用已有契约，仅保证尚未运行的排队任务取消。已运行的下载使用超时和暂存清理，失败可重试。外层授权最初计划通过新部署配置交付；按服主反馈改为随签名发布下发，玩家端核对目录结构一致才启用，不一致只跳过外层文件，没有新增本机授权弹窗（见 ADR 0041）。配置修改不会改变已运行 Java 进程的参数。三个启动器的新版本实机复测仍单独验收。

## 用户希望得到的使用方式

需要区分三种更新，它们各有自己的来源和发布操作。

| 更新对象 | 谁提供内容 | 服主如何控制 |
| --- | --- | --- |
| 玩家端程序的新功能和错误修复 | 梦鱼更新器官方 | 管理端发现新版，服主查看说明并批准指定版本，玩家下次启动时自动升级 |
| 服务器首页、公告、背景、音乐和其他个性化展示 | 服主 | 继续使用项目现有的个性化发布流程，程序升级保留这些内容 |
| 模组、游戏配置和指定的启动器周边文件 | 服主 | 检查改动后发布；外层文件需要事先配置更新范围 |

示例：官方发布程序 A，服主批准后，玩家自动取得 A。官方之后发布 B，管理端提示有更新，但没有经过服主批准的玩家继续使用 A。整个过程中，服务器自己的首页和整合包版本独立管理。

第一版采用“每个项目批准指定版本”的方式，不默认持续跟随官方最新版本。管理端提供“允许玩家端程序自动更新”开关和“批准此版本”操作。新项目默认关闭，首次启用时选择批准目标；已有项目迁移保留原来的有效发布状态。关闭开关暂停后续程序升级，不关闭整合包更新，也不会把已经升级的玩家自动降级。

这里控制的是该项目正常使用的更新渠道。玩家自行下载其他官方版本或修改本机文件，不属于这个开关能强制禁止的范围。

## 已有能力与需要补齐的部分

当前代码已经支持服主发布玩家端程序，然后由玩家端自动下载和切换。需要复用这条链路，补齐官方版本发现、自动准备、服主批准和暂停控制。

| 已有位置 | 当前作用 | 计划中的处理 |
| --- | --- | --- |
| `update-engine/.../PlayerProgramUpdater.java` | 从项目地址获取玩家程序清单，验证项目签名、版本和文件哈希，安装到新目录 | 复用下载和安装，增加更新策略检查与失败版本处理 |
| `player-app/.../PlayerController.java` | 先检查玩家端程序，再检查整合包；需要切换时交回 Bootstrap Agent | 保留顺序，补齐策略和界面状态 |
| `bootstrap-agent/.../BootstrapRuntime.java` | 启动已选择的程序，新程序未授予许可便退出时可以尝试旧程序 | 验证回退边界，避免反复启动失败版本 |
| `management-core/.../PlayerProgramService.java` | 将服主选择的程序目录发布为项目签名版本，并立即更新当前版本指针 | 拆分准备候选版本与批准生效，避免检查或下载就自动推给玩家 |
| `admin-desktop/src/workbench/DeliveryView.vue` | 上传 ZIP 或选择目录发布玩家端程序 | 加入官方版本、批准、暂停和实际生效状态 |
| `protocol/.../ProjectBinding.java` 与 `Branding` | 项目连接和个性化信息独立于程序版本 | 保持独立，验证程序升级前后数据保留 |
| `protocol/.../PathSafety.java` | 阻止文件路径逃出当前更新范围 | 保留保护；只在配置更新根目录时解释父级关系 |
| `docs/adr/0022-self-update-the-player-app-but-not-the-bootstrap-agent.md` | 玩家程序可自更新，Bootstrap Agent 不在线替换 | 沿用；需要新版 Agent 的发行单独提示重新部署 |

目前的实例目录由 Agent 所在位置确定，并且模组识别、安装、备份、恢复等操作都以它为基础。不能只把一个根路径改成上级目录，否则原本的 `mods/` 含义和历史恢复位置也会跟着改变。

## 第一阶段 明确协议和兼容边界

先确定可测试的行为，再编写界面。

1. 程序版本、整合包版本、个性化内容版本继续分开。管理端使用清楚的名称，避免服主把“更新玩家端程序”理解成“更新整合包”。
2. 官方程序目录按玩家程序版本和平台标识。管理端版本、GitHub Release 标签不能替代玩家端版本；一次 Release 可能只更新管理端。
3. 官方版本目录至少包含玩家程序版本、平台、文件大小和哈希、官方签名、更新说明、最低 Agent 版本、管理端导入要求及协议能力要求。先覆盖当前已有的平台，不因界面上增加选项而宣称支持新平台。
4. 项目更新策略独立保存，包含是否启用、各平台批准的版本及清单摘要、递增的策略修订号。相同版本但摘要改变时拒绝接收，继续保留现有的防替换和防重放保护。
5. 新功能必须有明确的能力标识和最低玩家端要求。旧程序不能忽略新字段后继续执行一半更新。
6. 保留旧项目的有效版本和历史签名，不重新签写历史清单。升级管理端时迁移已有发布状态，不擅自批准官方尚未采用的版本。

Agent 兼容检查需要对应玩家实际安装的 Agent。目前玩家侧传入的是 `PlayerRuntime.BOOTSTRAP_AGENT_VERSION` 常量；增加官方版本适配时，需要确定可验证的实际版本来源。无法取得实际版本的旧部署采用保守兼容规则，不能因为新版玩家程序携带了新常量就认定旧 Agent 也升级了。

需要新增架构决策记录，说明官方签名与项目签名的分工、批准的生效规则，以及实例目录和整合包目录的关系。

验收条件：能用行为表明确回答“服主关闭时会怎样”“已有玩家怎样首次得到此能力”“旧 Agent 能否使用此版本”“旧玩家遇到新目录清单时会怎样”。

## 第二阶段 管理端发现并准备官方玩家端版本

### 官方发行

在现有正式发行流水线中，生成独立的玩家端版本信息和可验证的程序载荷。只含管理端更新的 Release 不应让管理端误报玩家端有新版。

官方下载保留现有发行包，另外明确可自动导入的程序文件范围。自动导入不能把首次部署包中的项目绑定、示例设置、运行数据或空目录当成需要覆盖玩家的数据。

官方签名用于证明下载内容确实由官方发布。管理端验证官方签名和完整文件清单后，服主批准，才使用项目签名发布到自己的玩家更新渠道。不能只从同一下载位置取得一个哈希文件便视为验证了来源，也不能把桌面管理端安装包的签名协议直接当作玩家端协议使用。

官方签名密钥只进入受控的发行流程，不分发到管理端。定义公钥固定、后续轮换和旧版本验证方式；项目私钥继续留在服主管理环境。

### 管理端准备

增加“检查官方玩家端版本”和“准备此版本”任务。流程为获取目录、验证兼容性、下载、验证签名与文件、生成候选记录。候选记录绑定确切版本和摘要，批准前再次检查项目状态是否变化。

程序准备在管理服务所在电脑或服务器执行。桌面端、网页端和 CLI 使用同一套管理服务能力；连接远程管理服务时，不能只把文件下载到服主桌面后便显示服务器已准备完成。

检查和准备均不改变玩家当前可获得的程序。已有的手动 ZIP 导入和目录发布继续保留，但也经过清楚的准备与确认步骤。

使用现有任务系统提供进度、取消、错误详情和重新尝试。网络检查使用缓存、有限重试和退避，支持手动刷新；不让每个玩家频繁查询 GitHub，也不在每次管理界面刷新时重复下载大文件。程序文件尽量复用现有按内容哈希保存的对象。

验收条件：官方目录不可达、下载中断、签名错误、平台不符或缺少文件时，不改变项目当前程序；只检查和准备新版，玩家不会自行收到它。

## 第三阶段 服主批准和暂停程序更新

### 管理界面

在“发放 → 玩家端程序”增加以下内容：

- “允许玩家端程序自动更新”开关，旁边说明只影响程序本身，模组与配置照常更新。
- 各平台当前已批准版本、可用官方新版、更新说明和兼容性提示。
- “准备此版本”“批准此版本”“暂停程序更新”操作，以及尚未应用到下载服务的状态。
- 对旧 Agent 明确提示“需要重新制作并分发玩家实例”，不能承诺自动替换已经加载进 Minecraft 的 Agent。

批准针对确切版本，不使用一个将来可指向任意版本的“最新”别名作为服主授权内容。多平台分别显示结果；没有准备成功的平台继续保留原状态，不能显示为全部完成。

### 更新策略与现有发布链路

增加由项目签名的程序更新策略，并在动态下载服务和静态导出中一致使用。程序正式生效前，应先准备好所有不可变对象及清单，最后切换可变的批准状态和下载入口。

需要特别处理旧玩家：旧程序不会执行新增加的策略字段，因此不能只在新玩家端写一个开关。动态服务必须同步控制旧的 `/player/<平台>/latest`、`.sig`、`.signed` 等入口；暂停时使旧客户端按它们已支持的“没有发布程序”行为继续检查整合包，而不是继续暴露未获准的新目标。确切响应和新旧入口的切换顺序需要用真实旧版验证。

静态托管也必须更新同样的入口。暂停时若需要移除旧入口，导出与上传流程应生成受限的移除计划，只处理该项目拥有的可变入口，不删除历史程序、共享对象或用户其他文件。仅在本地导出目录删除文件而云端还保留旧入口，不能算暂停成功。验证 `.signed` 与旧 `.sig` 回退、真实 404、浏览器或 CDN 缓存，以及部分上传失败的情况。

管理端明确区分以下状态：策略已保存、动态服务已生效、静态文件待上传、静态上传失败。使用 OSS、WebDAV 或自行部署 HTTP 的服主，应看到本渠道尚待完成的操作。

已有项目迁移保留当前已发布的授权目标。关闭后再开启时仍使用已批准目标，批准后续版本需要单独操作。不得把批准指针下调来实现回滚，否则会与现有防降级检查冲突。

### 玩家侧执行

玩家从自己的项目更新地址取得项目策略和已批准程序，验证项目身份、策略修订、平台、版本和文件。正常流程继续由服主的服务或外部托管分发；官方源不可达不应影响已经准备好的项目更新。

下载到临时目录，完整验证后安装到新的版本目录，再通过现有 Agent 切换程序。激活前重新核对能够取得的最新批准状态；发现暂停、目标变化或权限状态无法可靠确认时，不激活候选版本，保留当前可用程序。

程序升级失败时，只在当前程序仍支持整合包要求的情况下继续。若整合包使用了当前程序不认识的必要能力，应清楚提示缺少哪个版本，不能忽略规则后放行。管理端也要在发布前拦截“暂停程序更新，但新整合包要求玩家尚不能取得的新程序”的矛盾配置。

暂停有传播时间：已离线的玩家无法即时取得新策略，静态上传和缓存也可能延迟。已经完成切换的玩家保持现版本，正在使用旧策略或旧程序的在途更新也不能承诺瞬间撤回。文案与测试应反映这个边界。

### 个性化和失败恢复

程序载荷只包含程序文件。项目连接、公钥、首页、公告、背景、音乐、本地偏好、模组启停、备份和日志都保留在各自的数据位置。若新版需要迁移本地数据，使用独立的数据格式版本、迁移备份和崩溃恢复记录；新程序迁移失败时，不能留下旧程序也读不了的数据。

保留已验证的上一版本作为启动失败时的恢复选择。记录失败版本摘要，防止每次启动都下载或切回同一个坏版本。启动许可成功只证明启动流程可用，不能当作所有新功能都已健康；需要测试不同失败时点。

第一版不提供任意远程降级。官方问题版本通过暂停后续采用、保留已知可用程序，以及发布更高版本的修正版处理。将来如增加降级，必须单独设计授权和防重放规则。

验收条件：两个项目可批准不同版本；关闭后不再交付新的程序升级；官方后续版本不会绕过批准；个性化与本地数据保留；失败后可恢复，并且不会陷入重启循环。

## 第四阶段 自定义外层文件更新目录

### 目录使用方式

保留原来的游戏实例目录，增加可选的“整合包外层目录”。服主为外层文件设置相对起始位置，并选择实际要维护的文件。

例如玩家目录如下：

```text
玩家整合包/
  新玩家进服教程.txt
  launcher-theme/
    background.png
  .minecraft/
    versions/
      梦屿1.21.1/
        mods/
        config/
        .dreamingfish-bootstrap/
```

从 `梦屿1.21.1` 向上三级，可找到 `玩家整合包`。界面可以表达这种与 MCPatch 起始目录类似的用法，同时展示实际解析位置和待更新文件，避免让服主只填写难以理解的层级数字。

`mods/` 和 `config/` 继续属于游戏实例；教程和背景属于外层目录。两者有明确的目录标识，发布清单内部使用“目录标识 + 安全相对路径”。`../../../` 只用于确定已允许的起始目录，具体文件路径仍不能包含跳出目录的片段。

### 允许范围

外层目录以 Agent 所在实例为锚点，并在本机绑定中明确记录允许范围及目录身份。不能直接信任启动器当前工作目录，因为不同启动器可能给出不同位置。整合包整体移动后，相对布局仍应可用。

仅有远程签名清单，不能把本机原本的实例更新范围静默扩大到桌面、用户目录或整个磁盘。新部署包可以预先配置外层范围；已有玩家首次扩展时需要明确的本机确认或新的部署配置。目录找不到、身份不符、解析到不允许位置时，停止外层更新并给出可操作的提示。

游戏目录包含在整合包外层目录中时，禁止两种目录标识指向同一个托管文件；外层文件清单不能再次接管实例目录。保护 Agent、更新器程序与数据、存档、截图、账户、令牌等位置。默认不扫描整个启动器目录，只维护服主明确选中的条目。

继续检查符号链接、Windows junction、绝对路径、磁盘根目录和等价路径别名。操作前再次验证目录身份，不能只在预览时验证一次。

### 引擎改造范围

目录标识必须贯穿扫描、清单、维护规则、差异计算、下载计划、用户偏好、安装事务、备份、恢复、停止维护、历史问题删除和回滚。模组识别仍针对游戏实例中的 `mods/`，不因外层目录引入而失效。

共享同一外层目录的多个实例需要共享更新锁，并考虑另一个实例或启动器正在使用文件的情况。锁的身份以实际共享目录为准，不能只靠单个实例内的锁。被占用文件不能通过反复强行覆盖来处理。

一次发布同时更新两个目录时，先下载和验证全部内容，再记录带目录标识的事务。多目录事务要支持中途崩溃、文件占用、空间不足、跨磁盘复制失败和恢复；不能把多次文件移动描述成天然的全局原子操作。恢复前确认目录还是原来绑定的位置，避免把历史备份还原到另一个目录。

旧项目默认只有游戏目录，不要求重新创建项目。旧清单与历史备份按旧语义读取。首次使用外层目录时生成新基线并要求支持该能力的玩家端；先完成第三阶段的升级路径，再发布这种整合包内容。

验收条件：能更新实例外的指定教程和背景；游戏模组规则保持有效；未列入维护的其他文件保持原样；非法目录被拒绝；移动整包后仍能解析；多实例和中断恢复不会写错位置。

## 第五阶段 启动器配置和参数适配

目录功能解决“文件放在哪里”，并不能自动保证“修改启动器配置的方式正确”。这一阶段以 PCL、HMCL、美西螈启动器的真实文件与运行行为为依据。

先列出每种启动器确实需要维护的配置文件、格式、目标字段、读取时间、写回时间和占用行为。教程、图片等独立文件可以完整替换；混有账户、内存设置、Java 路径和玩家偏好的配置文件，需要按字段修改，不能默认用服主文件整体覆盖。

配置合并只针对已验证的文件和字段：保留未知字段与玩家账户，识别版本差异；格式无法识别或有冲突时备份并提示，不能猜测后写入。启动器运行期间会把旧值写回的配置，安排在其支持的安全时机应用。

版本 JSON 中的 JVM 参数需要保持原有数组及条件参数，避免重复添加 Agent。保留已验证的相对 Agent 参数用法，并在三个启动器中重新验证，不能因为 JSON 文本正确就判定接入成功。

通过 Agent 开始检查更新时，本次 Java 进程的 JVM 参数已经生效。此时改动启动器设置或版本 JSON，不能改变当前已经运行的 Java 参数。界面和教程明确提示何时需要退出并重新启动游戏或启动器；若未来要求参数在同一次启动前生效，需要另行增加启动器前置流程。

验收条件：PCL、HMCL、美西螈分别完成“修改文件 → 关闭并重开 → 读取实际设置 → 启动玩家端 → 授予游戏启动许可”的验证；账户、玩家偏好和已有 Agent 接入不被破坏。

## 实施顺序与交付条件

| 顺序 | 交付内容 | 进入下一步的条件 |
| --- | --- | --- |
| 1 | 协议约定、架构决策、兼容行为表 | 旧玩家、旧 Agent、暂停和静态托管行为明确 |
| 2 | 官方玩家端目录、签名、管理端准备任务 | 候选程序验证成功，未批准时不会对玩家生效 |
| 3 | 服主批准、暂停、玩家执行、数据保留与恢复 | 动态和静态渠道的新旧玩家测试通过，可独立交付 |
| 4 | 外层目录、规则、事务、锁和备份恢复 | 全路径链路识别目录身份，拒绝越界和重叠托管 |
| 5 | 启动器字段适配和教程 | 三种启动器真实测试通过，说明参数生效时机 |
| 6 | 发行验证与交付 | 文档、构建、签名、资源审计和发布规则通过 |

优先让服主更容易把新版玩家端交到已有玩家手上，再引入需要新版支持的外层文件规则。已完成但尚未提交的界面和填写历史改动单独保留，不能在这次实现过程中丢失，也不能把它们误记成目录功能已经完成。

## 必须覆盖的验证

| 场景 | 应有结果 |
| --- | --- |
| 官方发新版，项目未批准 | 玩家程序保持原版本，管理端提示新版 |
| 只更新管理端的官方 Release | 不误报玩家端有新版本 |
| 只批准项目甲 | 项目乙保持其原有授权目标 |
| 准备新版但未批准 | 玩家更新入口不变 |
| 暂停程序更新 | 整合包仍正常检查；新旧玩家不会从项目入口得到新程序目标 |
| 下载中途暂停，或批准另一版本 | 新版按最新可取得的策略决定是否激活；在途和缓存限制有明确提示 |
| 官方源不可达、包签名或哈希错误 | 不发布候选；已有项目服务继续提供当前可用内容 |
| Agent 或平台不兼容 | 不批准到不支持的平台，提示正确的部署办法 |
| 程序升级后 | 服务器个性化、连接、本地偏好和备份完整保留 |
| 新程序切换或数据迁移失败 | 可恢复已验证的旧状态，不循环重启或破坏数据 |
| 静态上传一半失败、暂停入口未成功清理 | 不宣称完成，保留可重试记录与实际生效状态 |
| 新整合包要求新能力，玩家程序仍旧 | 发布前提示或拦截矛盾配置；玩家侧不给出错误放行 |
| 外层文件更新、删除和恢复 | 始终对应同一个允许目录和文件，其他文件保留 |
| 路径越界、目录替换、链接、重叠托管 | 在写入前拒绝，原文件保持完整 |
| 两个实例共享外层目录 | 不并发覆盖，等待或给出明确占用提示 |
| 中文和空格路径、整体搬动整合包 | 身份和相对位置正确，不依赖服主电脑的绝对路径 |
| Windows 和 Linux | 目录权限、可执行位、锁和恢复行为符合对应平台 |
| PCL、HMCL、美西螈 | 从真实启动器启动，实际观察玩家端及游戏许可，配置在约定时机生效 |

协议和引擎使用单元及集成测试，动态下载使用真实本地 HTTP 链路，静态渠道覆盖导出、上传和客户端读取。故障注入放在激活、指针切换和事务提交等关键位置。GUI 自动化用于确认服主能看到并理解当前状态；真实启动器测试保留程序版本、配置差异和脱敏日志。

## 文档与发行

实现后同步更新 `docs/DEPLOYMENT.md`、`docs/ADMIN-WORKSPACE.md`、相应协议说明和架构决策。官网教程同步程序升级与目录配置的实际行为，不提前把计划写成已经可用的功能。

更新教程应分清：官方发布程序、服主批准程序、服主发布个性化内容、服主发布整合包，以及首次启用外层目录。程序升级后仍需服主发布个性化变更；普通程序更新也不等于重新分发整个整合包。

正式发布时按 `AGENTS.md` 和 `docs/RELEASING.md` 执行。同版本保留一条完整发布提交；CI 修正并入尚未正式发布的提交，保留用户更新摘要。发布说明最前面加粗说明玩家端采用办法、是否需要重新制作实例，以及桌面功能需要更新服主电脑上的桌面管理程序。每次保留完整更新教程，使用 `packaging/publish-release.ps1` 并先运行 `-DryRun`。

尚未实际通过的测试不能写成成功，计划不预先指定正式版本号或创建发布标签。
