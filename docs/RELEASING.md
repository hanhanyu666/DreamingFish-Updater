# 提交日志与 Release 规范

提交标题统一为 `[玩家 - 0.2.2][管理 - 0.2.8] 修复部署包下载，新增另存为与保存结果提示` 这样的格式。两个版本号分别对应实际程序，未更新的程序沿用原版本。正文说明用户遇到什么问题、现在如何解决及验证结果，不能用大量 CI 或内部重构细节代替用户可见变化。

同一版本在仓库历史中只保留一条完整的发布提交。推送后如果远程 CI、构建或测试发现问题，修正后使用 amend 或 squash 合并回本次尚未正式发布的提交，保留原来的面向服主的提交标题与主要更新说明；纯验证环境修正不单独新增用户更新日志，也不留下连续的“修复 CI”“兼容校验脚本”提交。只有实际功能范围或用户影响发生变化时，才相应修订更新说明。

更新已推送的本次提交前先 fetch，核对远端没有其他人的后续工作，再使用精确的 `--force-with-lease` 更新本次分支；远端出现其他提交时先保留并整合，不能强制覆盖。以最终通过验证的提交创建发布标签，再按下方流程发布。这个约定不授权追改已正式发布的历史提交或标签。

每次 Release 在 `docs/releases/v<版本>.md` 保存完整发布说明，正文标题使用同样的版本前缀。开头的加粗提醒明确哪些程序需要升级、服主是否需要重新发布玩家端程序；接着写更新内容、附件用途和本次完整更新教程。教程可以参考 [v0.2.8](releases/v0.2.8.md)，但不能省略为“与上次相同”或只放链接。

“更新教程”必须有以下六部分，且每部分包含实际步骤：

1. **升级前备份**：先完成正在执行的操作，找到实际管理目录；备份 `data/`、`management-settings.json`、`management-web-auth.json`、桌面连接与外部标准整合包目录，保留签名身份及恢复材料。
2. **Windows 桌面安装版**：如何检查更新或运行安装包，说明关闭窗口只是隐藏到托盘，手动安装前应真正退出；保留原安装位置与实际数据。
3. **Windows 桌面便携版**：解压完整程序到固定目录，退出旧进程后替换程序文件；不能用新包的空目录覆盖旧 `data/`，外部目录另行保留。
4. **Windows / Linux 终端管理端**：停止原服务，替换对应平台的程序与运行环境，保留设置、账户、数据和源目录，再按原方式启动。不能擅自改变现有监听配置或虚构 systemd 单元名称。
5. **玩家端是否需要更新**：明确本次是否需要发布新玩家程序；需要时写“发放 → 玩家端程序 → 上传 ZIP → 检查发行包 → 确认发布”的操作，不需要时明确告知。普通在线整合包更新不要求反复制作首次部署包。
6. **升级后检查**：核对实际版本、原项目、账户、发布历史、下载服务和本次修复功能；路径异常或数据看似为空时先核对原目录，不要重新建库或删除恢复记录。

更新版本时同步管理 CLI、桌面前后端、Cargo / npm 版本和锁文件、构建默认参数、版本断言、当前使用说明及 `CHANGELOG.md`。历史 Release 文档和历史审查记录不做机械版本替换。

正式发行须完成对应验证、构建、发行包审计和签名，推送按规范撰写的提交与注释标签。发布前运行：

```powershell
.\packaging\publish-release.ps1 -Tag v0.2.8 -NotesFile docs/releases/v0.2.8.md -DryRun
```

确认规划结果后使用同一入口去掉 `-DryRun` 发布。脚本在任何远程操作前检查发布说明标题、完整更新教程和附件，缺少教程或只有空标题会拒绝发布；有新桌面安装包时还需匹配的签名与 `latest.json`。发布后核对公开附件、校验文件、完整说明和自动更新下载地址。

包含中文的发布检查脚本保留 UTF-8 BOM，以兼容 Windows 自带的 PowerShell；发布规划测试会在 Windows 上调用该运行环境读取真实的教程校验脚本。

## 官方玩家端签名目录

管理端 0.3.2 起通过固定官方公钥校验 `player-catalog.signed`。这与桌面 Tauri 更新签名、服主项目签名是三套独立身份；不能互相替代。包含新玩家 ZIP 的 Release 必须同时提供匹配的签名目录，否则发布入口拒绝执行。

完成正常构建、测试和发行包审计后，使用同一批构建产物生成目录：

```powershell
$env:JAVA_HOME = '实际 JDK 21 路径'
# DFS_PLAYER_SIGNING_KEY 指向受保护的官方玩家端私钥文件
.\packaging\build-player-catalog.ps1 -Version 0.3.3 -Tag v0.3.2 -NotesFile docs/releases/v0.3.2.md
.\packaging\publish-release.ps1 -Tag v0.3.2 -NotesFile docs/releases/v0.3.2.md -DryRun
```

示例发布说明文件须先按本约定完整编写，版本、标签、ZIP 与说明必须一致。`build-player-catalog.ps1` 目前生成 Windows x64 条目；它读取已解压的 `dist/dreamingfish-player-windows-x64/DreamingFishUpdater/app/<玩家版本>`，签入程序逐文件哈希、ZIP 哈希、下载标签、说明及最低管理端 / Agent 版本。目录只授权程序载荷，不把首次部署的绑定或运行数据推到已有玩家。

本机当前私钥默认位置是被 Git 忽略的 `.tools/release-signing/official-player.pk8`，也可用 `DFS_PLAYER_SIGNING_KEY` 指定受控位置。正式发行前另做离线安全备份；不得复制到发行目录、日志、仓库或聊天。公钥在 `management-core/src/main/resources/cn/dreamingfish/updater/management/official-player-public-key.txt`。不要每次构建重新生成密钥，否则已安装管理端无法验证。当前使用单一固定公钥，没有自动轮换协议；需要换钥时必须单独发布管理端信任迁移，不能直接替换线上签名身份。

只更新管理端的后续 Release，发布脚本会携带并验证上一版 `player-catalog.signed`，保持玩家版本与原下载地址；不能重新签出同一玩家版本但不同内容。首次引入本能力的 Release 需要包含新玩家 ZIP 与新目录。`-DryRun` 只检查本地，实际发布还会检查需继承的远端目录；两者都不得绕过。签名目录暂未正式发布前，管理端检查官方版本会明确提示缺少该附件，手动 ZIP 发布仍可使用。

发布后的验证除桌面 `latest.json` 外，还要下载公开的 `player-catalog.signed` 验证签名与玩家版本，核对条目指向的 ZIP 确实可下载。随后在隔离测试项目中准备并批准，验证玩家从项目渠道更新，服主个性化与本地设置保留。签名成功或启动许可通过不代表所有启动器与配置格式都已实机兼容。
