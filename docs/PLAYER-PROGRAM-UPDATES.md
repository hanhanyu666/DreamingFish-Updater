# 玩家端程序的发布和自动更新

适用于管理端与桌面 0.3.2、玩家端 0.3.3 起。程序升级、服务器个性化内容和整合包文件更新分别管理。官方发布程序的新功能与修复，服主决定本项目采用哪个版本；程序升级保留服务器首页、公告、背景、音乐、连接配置和玩家本地设置。

## 程序文件从哪里来

当前实现的路线是：**官方 GitHub Release → 管理端 → 项目下载服务或 OSS 等托管位置 → 玩家**。这和服主手动上传玩家端发行包是同一种发布，区别只在于管理端替你从 GitHub 下载，并多核对一遍官方签名。服主点击“发布给玩家”后，玩家端下次启动时自动下载、安装和切换程序；玩家无需自己下载 ZIP，也不会直接访问 GitHub。

使用管理端内置下载服务时，发布后就能从该服务提供程序。使用 OSS 等静态托管时，玩家只能读到云端的文件，需要重新导出并上传程序文件及更新记录，可以使用管理端的“导出并上传”。在“外部托管”勾选“保存密钥”后，管理服务会在发布、暂停和自动发布后自动上传。仅暂停或恢复时，需要同步新的设置及必要的旧入口清理，不需要另外发布一份新版程序。

管理端先通过 GitHub API（`api.github.com`）找到 Release 附件，再从 GitHub 的文件存储下载；部分国内服务器打不开 `github.com`，但能访问这两个地址。API 不通或被限流时，再直接访问 `github.com`。测试预发布或镜像可以用环境变量 `DFS_OFFICIAL_PLAYER_CATALOG`（或 JVM 参数 `-Ddfs.officialPlayerCatalog`）指定其他 https 目录地址；无论从哪里下载，目录都必须带官方签名，程序文件也要和签名中的哈希一致。

没有采用“玩家直接从 GitHub 下载官方程序”的方案：国内玩家访问 GitHub 往往不稳定，而服主的下载服务或 OSS 本来就是玩家能稳定访问的地址；同时各服可以自己决定何时采用新版，不会因为官方某个版本有问题而所有服务器同时受影响。

## 新版工作区的操作

1. 打开“发放 → 玩家端程序”，在右上角选择玩家平台。
2. 点击“检查官方新版”。有比玩家当前版本更新的官方版本时，显示版本、大小和更新说明；“这个版本需要什么环境？”中显示最低管理端与启动组件（Agent）要求。目前发行工具生成 Windows x64 的官方目录；没有提供的其他平台不会显示版本。
3. 点击“发布给玩家”并确认。管理端在管理服务所在的电脑或服务器下载官方程序，核对官方签名和每个文件，再用本项目签名发布。每个平台分别发布，每个官方新版都要发布一次。发布会开启本项目的程序升级；项目原来处于暂停时，确认框会提示这也会恢复升级，其他平台此前发布的版本也恢复提供。
4. 若使用内置公共下载服务，服务按项目策略提供这个版本。若使用 OSS、WebDAV 或自行部署的静态 HTTP，重新导出并上传；已保存密钥并开启自动上传时，管理服务约半分钟后自动上传。
5. 玩家下一次启动时验证项目签名、文件哈希、程序版本和 Agent 兼容性，然后下载并切换程序。服主不需要为了普通程序升级让玩家重下整个整合包。

官方程序约 37 MB，由管理服务所在的电脑或服务器下载。国内服务器没有代理时，从 GitHub 下载可能每秒只有几 KB 到几十 KB，37 MB 可能要一两个小时。连接中断或 2 分钟没有收到数据时，管理服务会重新连接并从已下载的位置继续，15 分钟内一点数据都没收到或总计超过 6 小时才放弃；卡片上显示下载进度条，下载期间可以继续使用管理端、切换项目，项目也不会被锁住，关闭或刷新页面后回到卡片会继续显示进度。不想等了可以点进度条旁的“终止下载”：已下载的部分会删除，不会发布任何内容；程序开始保存后就不能再终止。觉得太慢时，也可以在自己电脑上点卡片里的链接下载 ZIP，再展开“手动上传玩家端发行 ZIP”发布，效果相同。

管理服务开着代理时，从 GitHub 下载会走代理：先看 `HTTPS_PROXY`（或小写 `https_proxy`）环境变量，没有时在 Windows 上读取系统代理（例如 Clash 等工具“设置系统代理”后的 `127.0.0.1:7897`）；`NO_PROXY` 中的地址和本机地址始终直连。只支持不带账号密码的 HTTP 代理，SOCKS 代理或需要登录的代理会改为直连。Linux 服务器可在启动管理服务前设置，例如 `HTTPS_PROXY=http://127.0.0.1:7890 ./dfs-admin web`。代理只用于下载官方玩家端，上传到 OSS、WebDAV 等外部托管仍按原来的方式连接。

下载失败、签名错误或文件不符时，不会发布任何版本，玩家继续使用当前程序。两个窗口同时操作时，旧窗口在下载前就会被拒绝，需要刷新后重新确认。

也可以展开“手动上传玩家端发行 ZIP”，先“检查发行包”，再“批准并发布”。从目录发布与交互终端的“发布玩家端程序”也属于服主明确发布，会启用本项目程序更新。选取的必须是程序目录，不能包含账户、私钥、运行状态或备份。首次部署包与通用玩家发行 ZIP 是不同用途。管理端里已有、但还没发布给玩家的更新版本，会在卡片下方列出，也可以直接“发布给玩家”。

官方目录为 GitHub Release 附件 `player-catalog.signed`。正式发行中还未提供这个文件时，检查会说明目录尚未提供，服主可继续手动上传 ZIP；这不会关闭项目原有的整合包更新。

## 自动发布官方新版

打开“官方发布新版后自动发布给玩家”后，管理服务每小时检查一次（官方目录缓存 6 小时，最多每 6 小时联网一次）；官方有比本项目更新的版本时，自动完成和“发布给玩家”相同的下载、核对和发布。打开开关后约 5 秒会先检查一次。

- 只在管理服务运行时检查。桌面版需要程序或托盘在运行；远程管理服务一直运行时持续检查。
- 项目处于暂停时不会自动发布，也不会自动恢复，卡片会提示“上次自动发布没有完成”及原因。
- 官方版本要求更高的管理端、签名不符或下载失败时，同样记录原因，下一轮再试。
- 自动发布本身只更新管理端和内置下载服务。使用 OSS 等外部托管时，在“外部托管”保存密钥并开启“发布后自动上传”，自动发布后会一并上传；没有保存密钥时，仍需手动导出并上传，玩家才会收到。
- 想先在自己的测试服试用新版的服主，保持关闭，手动发布即可。

## 暂停与生效范围

“暂停玩家端升级”只暂停本项目渠道的程序升级，模组和配置仍照常检查。已经升级的玩家保持现版本，不自动降级。“恢复玩家端升级”继续提供原来发布的版本，不自动采用后来出现的官方新版。暂停与恢复同时控制本项目所有平台。

新项目初始未发布任何程序，开关默认关闭。旧项目升级管理端后保留原有发布目标，不重新发布其他版本。策略有递增的修订号；两个窗口同时修改时，旧窗口必须刷新后重新确认。

卡片显示玩家现在可升级到哪个版本，或当前处于暂停状态。使用 OSS 等外部托管时，提示还需重新导出、上传；“文件已导出”不等于云端已更新。“本次设置已随最近一次上传发出”只代表管理端最近一次内置上传，不代表其他托管地址和 CDN 都已经同步。具体区别可展开“自己的下载服务和 OSS，操作有什么不同？”。

暂停时，动态服务为旧玩家使用的程序 `latest` 和签名入口返回真实 404，使旧程序继续检查整合包。新版玩家还会验证项目签名的 `player/policy.signed`。下载完成后会再次确认授权，变化时不激活候选。

离线玩家、旧程序正在进行的下载和 CDN 缓存可能延迟取得暂停信息，因此不能承诺瞬间撤回所有在途更新。玩家自己手动安装其他程序版本，也不属于项目开关能强制禁止的范围。

## OSS 和其他静态托管

内置上传按导出目录中的 `.dreamingfish-player-retirements.json` 清理本项目停用的程序入口，并检查它们确实返回 404。只处理形如 `v1/projects/<项目>/player/<平台>/latest`、`latest.sig`、`latest.signed` 的入口，不删除历史程序、内容对象或其他项目文件。

上传账户除写文件外，需要这些入口的删除与检查权限。删除失败、返回异步接受而尚未删除，或检查时仍存在，均不算暂停同步成功。错误会提示需要核对权限并重新上传。

自行上传时，必须同时执行清理计划中的入口删除；只把本地剩余文件覆盖上传，不会删除云端旧文件。保留不可变历史文件，将 `latest`、对应签名与 `player/policy.signed` 设置为不长期缓存。缺失入口应返回真实 404，不应重写成 HTTP 200 的 HTML 页面。

阿里云 OSS 的寻址方式选择 **Virtual hosted**。批准、暂停、重新启用或发布内容后，都要按所用渠道同步，管理端不能替你确认未经过内置上传的外部位置。

## 终端操作

以下 `<...>` 是需要替换的占位内容。先查询，再使用返回的确切版本、摘要和修订号。

```text
dfs-admin player updates <项目ID> --action status
dfs-admin player updates <项目ID> --action check
dfs-admin player updates <项目ID> --action publish --platform windows-x64 --version <玩家版本> --sha256 <官方目录中的archiveSha256> --revision <当前修订号>
dfs-admin player updates <项目ID> --action auto --enabled true
dfs-admin player updates <项目ID> --action prepare --platform windows-x64 --version <玩家版本> --sha256 <官方目录中的archiveSha256>
dfs-admin --json player list <项目ID> --platform windows-x64
dfs-admin player updates <项目ID> --action approve --platform windows-x64 --version <玩家版本> --sha256 <候选的manifestSha256> --revision <当前修订号>
dfs-admin player updates <项目ID> --action pause --revision <当前修订号>
dfs-admin player updates <项目ID> --action resume --revision <当前修订号>
```

`publish` 等于界面上的“发布给玩家”，一步完成下载、核对和发布；`prepare` 与 `approve` 仍可分两步执行，适合想先在管理端检查候选程序的情况。发布与准备时的摘要是官方 ZIP 的摘要，批准时的摘要是项目签名程序清单的摘要，两者不同。`status` 同时返回更新策略和自动发布设置。网页已统一为工作区，旧网址会自动跳转；也可使用参数式 CLI。

## 兼容性与恢复

玩家从项目地址取得批准版本，不需要每个玩家直接查询 GitHub。官方目录的有效缓存保留 6 小时；“检查新版”会显式刷新。目录与候选文件必须通过固定官方公钥验证，随后由项目签名发布。

Bootstrap Agent 不在线自更新。玩家从已安装 Agent 的构建身份读取版本；无法识别时按未知旧版处理，保留当前程序并提示重新制作实例。不能用新版玩家程序自己的版本常量推断旧 Agent 也升级了。

切换使用新程序目录，并保留已验证的上一版本。新版文件损坏可以重新修复；程序文件完整但启动失败、实际进入旧版回退时，会记住失败摘要，避免每次启动重复切换同一坏版本。防降级记录独立保留，回退不授权远程随意降低程序版本。第一版不提供任意远程降级。

程序升级暂不可用或新 Agent 不兼容时，继续使用当前程序检查整合包；当前程序不支持整合包必要能力时，不能忽略规则放行。外层目录和配置合并要求玩家端至少 0.3.3，发布整合包前应先把可用的新版程序发布给玩家。外层目录的设置随整合包发布下发，已有玩家不需要更换部署配置，见[自定义目录和配置合并](CONTENT-ROOTS.md)。
