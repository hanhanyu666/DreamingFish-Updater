# 自定义更新目录和启动器配置合并

管理端与桌面 0.3.2、玩家端 0.3.3 增加外层文件更新和声明式配置合并。原有游戏实例目录保持原义，模组识别、`mods/` 与 `config/` 的位置不变。两项功能都在“文件”页。

## 指定整合包外层目录

例如玩家文件布局：

```text
玩家整合包/
  新玩家进服教程.txt
  launcher-theme/background.png
  .minecraft/versions/梦屿1.21.1/
    mods/
    config/
    .dreamingfish-bootstrap/
```

在“文件”页点击顶部的“外层目录”（尚未启用时显示“未启用”），在弹出的设置里选择“向上 3 级”，或点击示意文件树中的“整合包”，再点“启用外层目录”。树中分别标出“游戏实例 · 从这里出发”和“更新根目录”，并显示相应的 `../../..`。也可展开“直接填写路径和目录结构”手动输入。它表示从玩家游戏实例向上三级，目标是这个专属整合包目录。不要填写服主电脑或管理服务器的绝对路径。

文件树是常见版本隔离布局的示意，不是玩家电脑的实时目录，也不会读取或改动实际文件。向上 1 级在示例中是 `versions`，2 级是 `.minecraft`，3 级是整合包；选择更多层级会展开更上方的目录。请按玩家整合包的真实结构核对，不能仅凭示例确认所有启动器都使用同样布局。非法路径不会标出更新根目录，也不能启用。

启用后，“文件”页的“外层目录”会进入这批文件，顶部提示“整合包外层目录”。在这里导入实际要维护的教程、图片等文件，再检查并发布。管理端不会扫描玩家电脑，也不会自动把整个启动器目录纳入维护；普通游戏文件继续在“整合包”里导入。

相对起始位置支持上方 1 至 8 级。已启用的位置和目录结构固定，不能直接改成其他父目录，以免历史事务和备份恢复到错误位置；“位置设置”此时只读，并说明原因。停止维护某个外层文件仍使用现有的“移出”操作。

管理端内部路径形如 `@pack/<目录身份>/新玩家进服教程.txt`，界面显示为“外层目录/新玩家进服教程.txt”。它用于区分游戏文件和外层文件，不是玩家电脑上需要创建的目录。具体文件路径仍不能包含 `..`。

## 已有玩家如何开始更新外层文件

**不需要重新分发整合包，也不需要玩家手动替换文件。** 外层目录的设置随每次发布一起签名下发：

1. 先在“发放 → 玩家端程序”把玩家端 0.3.3 或更新版本发布给玩家。外层目录需要新版玩家端，发布整合包时管理端会检查这一点。
2. 启用外层目录、导入文件，检查并发布。
3. 已有玩家下次在线启动时，玩家端验证项目签名，核对本机目录结构，一致就保存这份授权并更新外层文件。

**目录结构核对。** 玩家端会核对从更新根目录往下到游戏实例的每一层文件夹名称。默认按版本隔离布局，向上 3 级时是 `.minecraft/versions/*`，`*` 表示任意名称（玩家改了游戏版本名也能对上）。玩家的实际结构不同时，例如把 `.minecraft` 改了名，或实例没有放在专属整合包里，玩家端**只跳过外层文件**，模组和配置照常更新，玩家端日志里写明原因；玩家把目录整理好后，下次启动会自动补上外层文件。服主的整合包结构不同的，在“直接填写路径和目录结构”里改，层数必须与向上的级数一致。

新生成的部署包同样包含这项设置，第一次运行即可离线使用。授权保存在实例的 `.dreamingfish-bootstrap/pack-root-grant.json`，部署包里的设置优先。第一次写入时，玩家端在专属整合包目录建立 `.dreamingfish-pack-root.json`，确认项目及目录身份；整合包整体搬动后，相对布局和身份仍可沿用。

目录解析到桌面、文档、下载、用户目录或磁盘根目录等过宽位置，或者目录身份属于其他项目时，同样只跳过外层文件。不能用手动删除身份文件的方式绕过，应先核对实际实例层级。

外层范围不接管 `.minecraft`、其他游戏实例、更新器程序和数据、存档、截图、常见账户文件或私钥。不同项目不能靠共用一个身份文件接管同一目录。

**为什么改为随发布下发。** 同一条更新渠道本来就能推送模组，模组是会执行的代码，所以本机单独授权挡不住被攻破的服务器；它真正需要防住的是层级填错、玩家目录不同导致写错位置。这由上面的目录结构核对、过宽目录拒绝、目录身份和“只写服主列出的文件”共同保证。

多个登记的实例共享外层目录时，写入共用目录需要共享锁；另一个实例正在运行时，不提交外层文件修改或恢复。没有外层修改的正常检查不因此强制禁止多个游戏实例运行。事务恢复前也核对目录身份；失败或中断时恢复本次涉及的原文件，不把多次文件操作称为全局原子提交。

终端可配置相同能力：

```text
dfs-admin project pack-root <项目ID> --relative-root ../../.. --layout ".minecraft/versions/*"
```

不填 `--layout` 时使用上面的默认结构。输出包含目录身份与管理端源目录。已有配置再次操作需提供 `--expected-id <当前目录身份>`；已授权的位置和目录结构不能通过这个命令直接改写。

## 合并启动器配置

在“文件”页右上角“导入文件”旁的下拉菜单选择“配置合并规则（高级）”；在外层目录里时，也可以点顶部提示里的“配置合并”。

这是修改现有配置中某几项设置的高级功能，玩家改过的其他设置保留。普通模组、图片或教程直接导入即可；只想第一次提供、之后交给玩家维护的配置，使用“首次提供”维护方式更简单。配置格式的选择决定修改哪类文件：Minecraft JVM 模式用于版本 JSON，INI 模式用于 PCL/Setup.ini 等文件；路径未填写时会说明检查按钮暂不可用的原因。

1. 选择“游戏实例目录”或已经启用的“整合包外层目录”。从外层目录打开时默认选中外层目录。
2. 填实际配置文件的相对路径，例如 `梦屿1.21.1.json`、`hmclversion.cfg` 或 `PCL/Setup.ini`。
3. 选择 Minecraft JVM 参数、JSON 字段合并或 INI 键值合并，并填写需要改动的参数或字段。
4. 点击“检查合并规则”，核对新增或替换的是规则文件，再点击“保存规则”。它复用导入的持久化收据、源文件备份和撤销流程，保存后规则文件出现在文件列表中。
5. 检查改动并发布。玩家端先备份本机配置，再合并指定字段；其余字段保留。

普通图片、教程可以完整替换。混有账户或玩家个人设置的启动器配置，应使用合并规则。系统拒绝规则直接修改账户、令牌及常见受保护个人设置字段，但不会替你识别所有启动器版本中的每个字段含义。

JSON 合并递归修改对象，保留未指定字段；数组按指定值替换。INI 默认处理无节的键，保留其他键和注释；同时识别 `键=值` 和 PCL 使用的 `键:值`，已有键保留分隔符，新增键沿用所在节已识别的格式。没有可识别条目的空 INI 默认使用等号；PCL 配置应以启动器实际生成的冒号格式文件为基础。重复的目标键会拒绝处理。支持 UTF-8，以及带 BOM 的 UTF-16LE。字段类型冲突、未知编码、配置超过 4 MiB 或规则超过 256 KiB 时，保留原文件并提示。

PCL“版本设置 → Java 虚拟机参数”对应游戏版本目录下 `PCL/Setup.ini` 的 `VersionAdvanceJvm` 项，这是 PCL 自己的设置。针对这个框使用 INI 合并时，只指定这一项，保留文件里的其他设置；但这一项的值是一整串参数，替换它仍会替换原来的整串文本，不会像下方 Minecraft JVM 规则那样逐项追加与去重。留空时使用 PCL 的全局设置，HMCL 等其他启动器也不会读取这项 PCL 配置。保存位置见 [PCL 设置源码](https://github.com/Meloong-Git/PCL/blob/main/Plain%20Craft%20Launcher%202/Pages/PageSetup/Settings.vb)。

## 规则文件格式

界面保存的源文件名称是在实际目标文件名后追加 `.dfs-patch.json`。例如 `hmclversion.cfg.dfs-patch.json` 是管理端的规则，玩家端修改的是 `hmclversion.cfg`，不会在游戏目录放置同名规则文件。也可以通过普通导入流程导入自己编写的规则。

JSON 字段合并示例仅说明格式，具体字段必须以目标启动器实际格式为准：

```json
{"schemaVersion":1,"format":"json","set":{"theme":"blue"}}
```

INI 键值合并示例：

```json
{"schemaVersion":1,"format":"ini","set":{"UiCustomType":"2"}}
```

有节的 INI 可增加 `"section":"Appearance"`。原文件的其他节不变。例子不代表任意启动器都具有这些设置。

Minecraft 版本 JSON 的 JVM 参数规则：

```json
{
  "schemaVersion": 1,
  "format": "minecraft-jvm",
  "addJvmArguments": ["-javaagent:.dreamingfish-bootstrap/bootstrap-agent.jar"],
  "removeJvmArguments": []
}
```

要求目标存在可识别的 `id` 与 `arguments.jvm`。保留原来的其他参数和条件参数对象；普通新增字符串去重，明确删除列表按完整字符串匹配。新增本项目 Bootstrap 参数时替换旧的同类参数，避免保留失效占位符或重复加载。其他 Agent 不被移除。规则拒绝改写常见个人内存参数、Java 路径和语言参数。

合并规则不能与其实际目标同时作为完整文件发布，也不能放在“清理多余文件”的目录内。移除规则时在“移出”里选择“停止维护，留给玩家”，不把玩家整个配置文件一起删除。历史备份保存合并前的完整本机配置，只留在玩家电脑上。

## 生效时间与启动器验证

Agent 开始检查时，本次 Java 进程已经启动。此时修改版本 JSON 或 JVM 参数，影响下一次启动，不能改变已经运行的 Java 参数。启动器也可能缓存配置或在退出时写回，因此要退出并重新打开启动器，检查设置是否保留，必要时在关闭启动器后核对文件。

通用相对 Agent 参数要求启动器保留版本 JSON 参数、工作目录能找到实例内的 Agent，实际游戏目录也指向该实例。PCL 的 `{verpath}` 回退参数只适用于 PCL，不能传给 HMCL、美西螈或普通 Java 命令行。部署包分别提供通用参数和 PCL 回退文件。

自动测试与实机启动器的验证范围分别记录，详见[本次验证记录](reviews/2026-11-01-implementation-verification.md)。相对参数并不保证任意启动器都保留同样的工作目录与版本 JSON 行为；配置规则也需要针对实际文件格式测试。
