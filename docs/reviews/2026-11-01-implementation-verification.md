# 玩家端升级、外层目录与配置合并：实现和验证记录

日期：2026-11-01。源码版本：管理端 / 桌面 0.3.2、玩家端 0.3.3、Bootstrap 0.1.2。随 v0.3.2 正式发布。

## 已实现的行为

- 官方程序先经过固定公钥校验，在管理服务机器准备候选；服主批准确切版本与摘要后，才进入项目程序更新渠道。后续新版仍需再次批准。
- 项目签名策略控制启用、暂停与各平台目标，修订号防止旧窗口覆盖。动态服务暂停旧程序入口；静态导出生成受限移除计划，内置上传删除并核查 404。分别记录本地导出和最近一次内置上传，避免把本地操作误报成所有云端均已同步。
- 玩家安装前后验证策略和程序；暂停或授权变化不激活。损坏文件可修复；已验证程序运行失败后进入回退时，记录失败摘要，防止循环切回，并独立保留防降级记录。Agent 版本来自实际安装 JAR 的构建身份。
- 外层目录从实例按固定相对关系定位，使用本机部署授权、项目目录身份与共享锁。其他实例占用、身份替换或越界时拒绝写入；备份、事务恢复和整体搬动保留相同目录身份。
- JSON、INI 和 Minecraft JVM 规则只合并指定内容，备份本机原文件；配置对象保存在独立的规则缓存中，使严格离线验证不依赖已清理的下载缓存。规则撤回选择停止维护，保留玩家配置。
- 保留此前未发布的外部托管填写历史、目录选择、OSS Virtual hosted 提示、选择器图标修正和明确删除文案。

用户操作见[玩家程序更新](../PLAYER-PROGRAM-UPDATES.md)和[目录与配置合并](../CONTENT-ROOTS.md)。签名发行流程见[发布约定](../RELEASING.md)。

## 实际 Windows 程序升级链路

使用正式构建脚本生成的 0.3.3 ZIP 与原有 0.3.2 ZIP，在全新的本机测试项目运行 `packaging/tests/native-player-update/NativePlayerUpdateProbe.java`。实际启动发行包里的 Tauri 窗口、Java sidecar 和 Agent；最后由一个独立测试 Java 主类输出许可标记，未加载 Minecraft 游戏或改动现有玩家实例。

结果通过：

1. 准备新版但暂停时，真实旧版 0.3.2 不升级，仍取得内容检查后的启动许可。
2. 批准新版后，旧版下载并切换，真实 0.3.3 sidecar 启动并取得许可。
3. 核对活动程序为 0.3.3，项目绑定的哈希、服务器个性化、整合包文件及本地数据哨兵均保留。
4. 未操作三个启动器界面，不把测试 Java 主类获许可等同于 Minecraft 已加载全部模组。

测试结束后仅清理本次创建的进程；窗口自动关闭动画与其他管理 / 玩家界面交互仍归入待复核项。

受限执行环境中的前两次窗口未进入 Java 引擎；常规 Windows 桌面环境使用同一批包通过。该结果表明失败不能直接归因于程序升级逻辑，但没有定位 Windows 初始化的具体限制。测试为子进程单独设置工作区内的 WebView2 用户数据目录，避免使用真实玩家浏览数据；该环境变量的含义见 [Microsoft WebView2 参考](https://learn.microsoft.com/en-us/microsoft-edge/webview2/reference/win32/webview2-idl)。成功证据为本机 `target/native-player-update-20261101/run3/result.json`、游戏许可日志和玩家更新日志；失败尝试也保留，没有覆盖成成功记录。
