# 远程 HTTP 测试失败的定位与修复

## 结论

v0.2.6 的管理接口与公共下载服务存在连接复用缺陷，并非所有远程失败都只是环境问题。修复进入管理端 / 桌面 0.2.7；玩家端仍为 0.2.2。

## 触发情况与原因

为了避免被慢上传拖住，服务设置 `sun.net.httpserver.drainAmount=0`，不在结束请求时自动读取剩余上传。Java 21 的请求输入流只有读到 EOF 才标记为完成：没有正文的 GET 也需要一次读取来确认这个状态。

旧处理没有统一确认此状态，也没有在提前拒绝上传时明确声明关闭连接。因此，响应看起来允许继续使用连接，JDK 实际却将其关闭。客户端紧接着发送下一次请求时，就可能遇到 `HTTP/1.1 header parser received no bytes`。远程失败发生在发布请求，以及拒绝错误上传凭据后的下一次上传请求。

通俗地说，服务端回话时没有告诉客户端“这条线要挂断了”，客户端下一句话仍往旧连接发送，结果收不到回复。

## 复现与修复

- 新增原始 TCP 回归：在同一连接上连续访问 `/healthz`。修复前在本机 Java 21.0.9 复现连接中断；修复后连续请求成功。
- 管理与公共 HTTP 入口使用同一连接生命周期过滤器。默认声明关闭，确认请求流结束后才允许复用；没有正文的请求只读取一次 EOF，不等待上传。
- 提前拒绝上传时保留 `Connection: close`，不主动读取剩余内容。原有并发、排队、停滞和请求时间限制保持生效。
- 测试覆盖固定长度正文、分块正文、同连接连续请求、不完整上传立即拒绝，以及客户端主动要求关闭。管理上传用例明确检查被拒绝响应的关闭标记。
- 发行脚本把 Maven 也绑定到指定 Java 21。此前打包运行环境使用指定 JDK，但 Maven 可能从默认环境选择另一份 Java，降低了本地与发行环境的一致性。

## 其他 CI 失败的区别

此前 Windows 换行与 Linux Maven 包装脚本执行方式的问题已修复。Maven Central 下载依赖时的 `Connection reset` 属于另一个网络失败，不能用本次 HTTP 修复声称它已经解决。远程完整验证以修复提交对应的 GitHub Actions 结果为准。

本地复现日志保存在 `target/ci-http-fix/`，属于本机验证材料，不是发行包内容。v0.2.6 标签和附件保留原样，修复版本使用独立编号。

本地修复验收：Java 21.0.9 下相关 HTTP、公共下载限流、管理接口、后台任务、CLI、桌面入口和 Bootstrap 发行产物验证通过；桌面前端 40 项与 Rust 38 项测试通过。修复前的失败测试与修复后的成功日志分别保留，未通过删除断言或自动重试写请求规避问题。

## 远程继续验证发现的 Windows 路径问题

HTTP 修复后，远程 Linux 完整验证通过，Windows 的 Java 阶段也通过；随后 Rust 阶段暴露迁移路径比较问题。连接加载会规范化路径，迁移边界却仍按原始文本比较。同一目录的 Windows 短路径或扩展路径写法不一致时，旧连接没有被重写，迁移后可能仍指向已经移走的旧目录。

本机新增 Windows 扩展路径回归，修复前复现“找不到路径”。修复后统一规范化已存在的祖先再拼接尚未创建的后缀，保留重叠目录拒绝和链接检查。便携测试按实际目录身份比较，同时额外断言保存的 home 必须为相对的 `management`，不是仅放宽路径断言。补修后本地 Rust 39 项通过。

## CI 验证输入与网络重试

远程 Windows 的完整代码验证随后通过。原生包检查在中文更新记录断言处失败：Windows 原生 CLI 参数受系统代码页影响。隔离发行包探针也确认，不能由本机代码页表示的表情字符在进入应用前变为问号。这不是 HTTP 历史接口改变了已保存内容，也没有通过删除中文断言规避。

整包检查改用现有且已文档化的 `--changelog-file` UTF-8 输入，ASCII 更新记录仍走直接参数；最终严格核对中文和表情字符。直接命令行参数的系统代码页限制仍存在，相关环境应使用 UTF-8 文件输入。

Maven 的依赖传输失败增加最多两次重试，保留每次日志并用 `-U` 重试被缓存的失败解析。仅匹配依赖/插件解析中的连接重置或超时，不重试测试断言、应用 HTTP 错误、编译错误或永久缺失依赖。独立测试覆盖这些区分。

后续远程 Windows 与 Linux 代码验证均通过，原生检查又暴露报告脚本直接向 cp1252 控制台打印中文的问题。控制台 JSON 现使用 ASCII 转义，UTF-8 报告文件继续保留原文；在强制 cp1252 环境中，五种模式的控制台 JSON 均与报告逐项相同。首次正常模式检测到延迟退出的 WebView 子进程，该失败记录保留；单独复查正常模式通过，未放宽退出检查。最终完整结果仍以修复提交的 CI 为准。
