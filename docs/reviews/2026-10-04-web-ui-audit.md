# Web 管理端 UI 与操作流程审查

本文保留改造前的问题和截图。对应 11 项已落实到新版工作区，操作说明见 [管理端工作区](../ADMIN-WORKSPACE.md)，实现与验证记录见 [完成记录](2026-10-04-admin-workspace-completion.md)。

日期：2026-10-04。审查对象：本机 0.2.0 管理端，Smoke Pack 演示项目。目标是让服主更容易整理文件、看清改动并发布给玩家。

本次通过内置浏览器重新查看九个主页面、文件夹展开、批量选择和多文件选择，保存并重新读取实际截图。常规窗口为 1064×871，另外检查了 720×800 的文件页。两份临时文本文件仅用于文件选择阶段，未提交上传；未发布整合包、修改维护方式、启动服务或提交设置。当前项目已有的待发布改动来自此前操作，全部保留。本次只增加审查记录。

总体判断：三种维护方式、批量操作、规则变化预览和真实玩家端预览已经构成可用的基础。最值得投入的是文件身份的可读性、上传前的明确反馈，以及常用功能与部署参数的层级。日常主线建议固定为“整理文件 → 查看改动 → 发布”。

## 优先处理

| 优先级 | 问题 | 建议 | 验收方式 |
| --- | --- | --- | --- |
| 最高 | 720px 窗口下文件名列实际宽度为 0px，维护方式和移除按钮仍显示 | 先保证文件名列有最小宽度；收起次要列或允许整表滚动。后续把目录导航和文件列表分开，窄窗口收起目录面板 | 在常见窄窗口中始终看得到文件名；不能出现只有维护方式和删除按钮的文件行 |
| 高 | 文件名、模组名与版本共用狭窄一行，元信息被截断；没有选择时仍显示整排禁用批量操作 | 文件名与模组名称/版本分两行；未选择时收起批量栏，选择后显示固定操作栏；详情抽屉展示完整路径、版本、规则来源和历史 | 能一眼区分模组及版本，查看详情不用依赖鼠标悬停；批量操作始终能看到作用范围 |
| 高 | 上传前只有数量和总大小，无法逐个检查目标或冲突 | 增加上传清单：文件、目标路径、识别的模组/版本、计划动作。逐项选择新增、覆盖、跳过；相同 modid 的新旧文件给出替换建议并由服主确认 | 同名冲突、同 modid 不同文件名及一批中的重复项，都在提交前显示明确处理结果 |
| 高 | 文件逐个上传；中途失败或取消后，前面的文件可能已导入，界面没有逐文件结果与只重试失败项的入口 | 维护上传任务清单及每项状态，区分等待、上传中、成功、失败、取消；只重试失败项。取消时明确已成功的文件仍保留 | 部分失败可恢复，不必重传已成功文件；显示已保存的数量和目标目录 |
| 高 | 上传目的地每次重新选，上传和服务器导入同屏；目录树的叶节点无法通过 Tab 选择 | 从当前文件夹发起添加时默认使用该目录，并显示可修改的路径；本机上传、服务器导入使用两个标签；目录树补齐键盘选择与焦点 | 用鼠标和键盘都能指定目的地；添加文件不需要重复找目录 |
| 中 | 待发布只在导航上用小标记显示，文件级未提供完整变更状态 | 用统一状态栏显示“已保存，尚未发布”和待发布项数；列表区分新增、已修改、维护方式变化、待移除。规则变化保留发布前摘要 | 服主能分清保存到服务器与玩家收到的时间；只改规则时不会误以为没有更新 |
| 中 | 部署页面出现平台、兼容版本、服务器路径等常填参数 | 平台从现有发行包中选择/识别，兼容要求默认计算后放高级选项；增加直接上传玩家端 ZIP 并自动检查目录结构的入口 | 发布程序不再必须先通过其他工具传包、解压和定位服务器目录 |
| 中 | 外部托管和实例部署同时展开多个互斥方案 | 先选托管方式，仅显示对应表单；“下载部署 ZIP”作为常用主按钮，写入服务器和直接制作实例放高级入口 | 无需读完其他方案的表单，也能完成自己的部署方式 |

## 文件页建议

顶部只保留搜索、筛选和“添加文件”。桌面宽窗口使用左侧目录导航和右侧文件列表；窄窗口把目录导航收进可展开入口。点击文件显示详情抽屉，日常列表不需要常驻所有字段。

文件首行显示完整可辨认的文件名，第二行显示模组名称和版本。维护方式保持普通同步、强制同步、首次提供三种，额外注明“继承 mods/”或“单独设置”。例如当前 mods/ 是普通同步但其中一个文件单独强制，可以给目录显示“普通同步 · 1 项单独设置”，帮助服主看懂例外。

当前全选和部分选择状态已有反馈，应保留。批量操作栏改为选择后出现，注明已选择的文件数量、所在范围；切换筛选时，如果保留其他目录的选择，要明确提示隐藏的选择数量。

切换整个目录为强制同步前，应预览涉及的文件、将被统一的单独设置以及玩家自加文件会被移入备份的范围。单个文件的普通调整可以继续即时保存。主列表也要显示空文件夹：现在上传目录树考虑了 directories，而主列表由文件构造树，空目录不会得到相同的展示。

## 上传流程建议

建议使用“在当前目录添加 → 选择文件 → 检查上传清单 → 导入 → 查看待发布改动”。普通上传默认继承目标文件夹的维护方式，不强迫服主逐项选模式。

| 上传清单中的情况 | 默认建议 | 服主看到的结果 |
| --- | --- | --- |
| 全新的文件 | 新增 | 保存到 mods/B-1.1.jar |
| 目标路径已存在 | 请求明确选择覆盖或跳过 | 原文件先归档，显示覆盖前后信息 |
| B-1.1.jar 与已存在的 B-1.0.jar 具有同一 modid | 提示更换旧版本，服主确认 | 明确列出加入新文件和移出旧文件；沿用维护方式与可选组归属 |
| 配置目录上传 | 保留相对目录结构 | config/example/client.toml，而不是全部放平到一个目录 |
| 某个文件失败 | 其他任务结果保留 | 失败原因、重试这一项、已成功项数量 |

目前浏览器文件输入支持 multiple，拖入后读取 dataTransfer.files，目标路径由目录加 file.name 形成，尚无保留文件夹结构的上传入口。整个文件夹的导入需要增加相对路径处理和验证。模组身份识别、批量预检及恢复上传清单需要接口配合，不能只靠样式完成。

同名覆盖目前确实会在服务器归档旧文件，这是现有的优点。界面可以进一步提供“查看归档 / 撤销这次导入”的入口；这需要明确撤销作用范围、保留后续修改，并让已发布项目通过新发布传达恢复结果。

## 视觉与交互统一建议

保留现有深色底色和青色品牌色。统一表格、按钮、弹窗、状态标签、间距和字重，避免继续在长样式表后面逐次覆盖。当前模组元信息实测为 11px，部分提示比正文弱得多；常用正文可提高到 14px，辅助信息提高到 12–13px，再结合实际窗口验证。

每个操作区域确定一个主操作，其余使用次要按钮或更多菜单。主按钮、错误、提醒、普通帮助各自保持一致的颜色用途。三种方式的大段说明可以压缩为简短说明和帮助入口，长表格保留固定表头。

个性化页面按“标题与品牌、外观、音乐、公告与页面”分标签。当前 1240px 以下把真实预览放在表单前方，编辑时需来回滚动；窄窗口使用编辑/预览切换，宽窗口保留已有固定预览。标题/配色保存后获取、图片/音乐须随整合包发布的不同生效时间，应在各区明确显示状态，不能给所有个性化操作相同的待发布提示。

将程序发布、部署包、外部托管组织到“发放与部署”分组。项目设置继续保留项目含义，监听端口等放“系统设置”，不要把项目下载地址与服务绑定地址混成同一个字段。

## 可访问性与证据范围

上传目的地树的叶节点为 role=treeitem 的 div，实测 tabIndex=-1，内部展开按钮又为 disabled。代码只有 click 选择处理，没有对应的目录选择键盘逻辑，因此仅用键盘无法完成这份样例中的目的地选择。新增目录输入也没有关联 label。文件页的重复“移除…”按钮可加上包含文件名的可访问名称。

深色界面的辅助文字偏小、部分灰字偏弱，可从截图和计算样式看出。未做完整对比度测试、屏幕阅读器验证、全部表单错误验证或可访问性合规评估。应单独验证键盘焦点、错误提示读取及缩放显示。

本次没有执行实际上传、覆盖、取消传输、故障注入、程序发布或外部托管。上传部分成功、取消后仍有已完成文件等结论来自现有上传循环和归档代码，未把这些情况称为已验证的浏览器行为。相同 modid 检查建议针对上传前预检，不代表断言后续扫描完全没有校验。示例只有 8 个文件，没有测试上千模组的性能；虚拟列表等优化应在实际负载测量后决定。
