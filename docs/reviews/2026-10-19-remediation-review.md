**一、本次确认的问题**

以下 F 编号属于本次复核，避免与原报告 R1–R12 混淆。P1 为建议发布前优先处理的正常使用回归；P2 为明确条件下的正确性或恢复缺口。

| 编号 | 优先级 | 问题 | 验证方式 |
| --- | --- | --- | --- |
| F1 | P1 | 桌面代理丢掉异步任务请求头，完成的操作留在“排队中”并禁用项目切换 | 当前 Rust 代理传输复现，当前 store 状态复现，界面控制流核对 |
| F2 | P2 | 导入复制中断产生半截临时文件后，后续恢复反复拒绝，项目检查被阻塞 | 人工构造中断后的磁盘状态，调用当前提交与恢复入口 |
| F3 | P2 | 第二个进程查询任务，会把另一进程仍在执行的任务写成“结果未知” | 活动任务与独立 Java 子进程复现 |
| F4 | P2 | 同一上传 ID 携带不同目标被拒绝后，原有有效暂存也被删除 | 当前 SourceTransferService 动态复现 |

**F1：新后台任务协议没有完整经过桌面代理。**

新版工作区在发起扫描、发布、导入提交等请求前，会先生成任务 ID，并发送 `Prefer: respond-async` 和 `X-DFS-Request-Id`。Java 只有收到这些头才创建后台任务并返回 202。[前端请求](D:/Desktop/DreamingFish-Updater/admin-desktop/src/workbench/store.ts:85)；[Java 判断](D:/Desktop/DreamingFish-Updater/management-cli/src/main/java/cn/dreamingfish/updater/management/cli/TaskHttpHandler.java:34)

但 Rust 代理的请求头白名单只包含 Content-Type、Content-Length、X-DFS-Token、Range 和 Accept，两个新任务头没有被转发。[遗漏位置](D:/Desktop/DreamingFish-Updater/admin-desktop/src-tauri/src/workbench.rs:177)

探针直接引用当前生产 `workbench.rs`：同一个 POST 直连测试上游返回 202，上游看到两个头；经过真实代理返回 200，上游看到两个头都不存在。随后用真实 store 接收这种同步成功响应，得到：操作结果正常返回，但本地任务仍为 `QUEUED`。因为前端只有收到 202 才进入任务轮询，200／201 分支没有结束预先创建的任务。[状态处理](D:/Desktop/DreamingFish-Updater/admin-desktop/src/workbench/store.ts:88)

通俗场景：服主在桌面端点击“检查改动”，Java 实际完成了扫描，改动结果也能回来；界面旁边却仍显示一个排队任务。这个任务又参与页面锁定计算，于是“切换项目”被禁用。查询或取消该任务时，服务端根本没有这个 ID；断线后的按 ID 复查也无法成立。[界面锁定](D:/Desktop/DreamingFish-Updater/admin-desktop/src/workbench/App.vue:25)；[项目按钮](D:/Desktop/DreamingFish-Updater/admin-desktop/src/workbench/ProjectPicker.vue:14)

这影响管理桌面的本机、HTTPS 和 SSH 连接，因为它们共用代理。直接访问管理网页不经过这层代理，因此网页的异步测试通过不能证明桌面流程正常。

建议在代理白名单中明确支持任务协议头，保持现有认证和 cookie 隔离；前端同时妥善处理异步请求收到同步成功响应的情况，不能遗留永久排队状态。新增一条真实工作区协议 → Rust 代理 → Java API 的集成用例，检查 202、相同 taskId、最终成功、回执丢失后复查，以及完成后项目选择恢复可用。正常隐藏窗口启动与 IPC 检查不足以覆盖这一项。

**F2：恢复知道要做什么，却无法处理自己复制到一半的临时文件。**

`SourceImportRecovery.replace()` 使用固定的事务临时文件名。如果临时文件已经存在，它要求内容立即符合完整目标哈希；只有文件不存在时才重新复制。[实现位置](D:/Desktop/DreamingFish-Updater/management-core/src/main/java/cn/dreamingfish/updater/management/SourceImportRecovery.java:152)

正常中断可能发生在 `Files.copy()` 内部，而不是只发生在复制完成之后。这时临时文件已创建，却只包含一部分内容。下一次恢复看到它存在，校验失败并保留；再试一次仍然看见同一个坏临时文件，仍然失败。

本次探针构造了这类磁盘状态：有效 payload 和任务身份仍在，事务专用 `.dfs-import-...tmp` 仅有部分内容。当前提交失败，随后调用项目扫描触发恢复，依旧被拒绝；目标文件未安装，半截临时文件保留。**这是构造中断后状态的恢复验证，没有声称本次做过真实断电，或在复制中途实际杀进程。**

对服主而言，表现是“一次导入失败后，原文件和上传内容还在，但整个项目一直提示需要恢复，重新检查也走不下去”。保护材料、防止不明覆盖是正确的；对于有可信事务身份、且可从完整 payload 重建的临时副本，还需要明确的自动重建路径。

建议在核对事务身份、原目标、payload 和归档后，隔离或清理本事务未完成的 scratch，再重新生成并校验。仍要拒绝覆盖后来被人工修改的游戏文件或源文件。新增复制中途失败、部分临时文件、重复恢复及撤销复制中断的测试。当前 [恢复测试](D:/Desktop/DreamingFish-Updater/management-core/src/test/java/cn/dreamingfish/updater/management/SourceTransferRecoveryTest.java) 的阶段退出点主要落在完整复制之后，不能替代此场景。

**F3：打开另一个终端看进度，可能改变任务状态。**

每次创建 `ApplicationTasks` 都调用 `loadInterrupted()`；它把磁盘中的 QUEUED、RUNNING、COMMITTING 改成 UNKNOWN 或 WAITING_FOR_INPUT，没有先证明原任务所属进程已经退出。[恢复判定](D:/Desktop/DreamingFish-Updater/management-core/src/main/java/cn/dreamingfish/updater/management/ApplicationTasks.java:118)

CLI 的 `tasks` 查询也会通过 `root.services()` 创建这套对象。因此，在桌面／网页服务执行长任务时，另开一个 CLI 进程查询，可能被当作“服务重启后的恢复”。[CLI 查询入口](D:/Desktop/DreamingFish-Updater/management-cli/src/main/java/cn/dreamingfish/updater/management/cli/TasksCommand.java:10)

本次让一个任务保持实际运行，再启动独立 Java 子进程读取同一人工管理目录中的任务。结果为：原进程内状态仍是 RUNNING，子进程读到 UNKNOWN，磁盘记录也已写成 UNKNOWN。这个状态差异不是模拟服务重启，因为原进程和任务一直存活。

这会使任务查询、取消入口和断线复查建立在错误的生命周期判断上。此次没有复现重复发布或文件丢失，不能把状态错误扩大成这些后果。

建议将只读任务查询与执行器恢复分开。只有取得执行器／任务所有权、确认原执行者失效后，才转换中断状态；查询进程不应抢写状态。可采用带进程启动身份的所有者记录、租约或唯一执行器控制入口，具体方案要兼顾 PID 复用和真实崩溃。至少新增“服务进程正在执行，CLI 同时查询”和“原执行者退出后才标未知”两种跨进程测试。

**F4：拒绝错误的重试请求时，误删了原上传。**

`SourceTransferService.stage()` 发现相同 requestId 对应不同目标路径时会拒绝，这是正确的身份保护；但是该异常进入外层统一 catch 后，又调用 `discard(projectId, id)`，把原来的有效、尚未提交的暂存删除。[冲突判断](D:/Desktop/DreamingFish-Updater/management-core/src/main/java/cn/dreamingfish/updater/management/SourceTransferService.java:45)；[无条件清理](D:/Desktop/DreamingFish-Updater/management-core/src/main/java/cn/dreamingfish/updater/management/SourceTransferService.java:64)

探针先用一个稳定 ID 上传 `config/first.txt`，再用相同 ID 请求 `config/second.txt`。第二次正确报错，但第一次的 stage 已不存在：`rejected=true originalStageRetained=false`。

通俗地说，本来应当回答“这个单号已用于别的文件，请换一个”，现在同时把原单号对应的货物丢掉了。受影响的是管理端上传暂存，没有在本次复现中删除玩家文件或已发布内容。

建议把既有身份校验与新建暂存失败清理分开，只有本次请求确实创建且拥有的未提交数据才可回收。拒绝冲突、检查既有 stage 失败、重复请求等分支必须保留原暂存。新增断言：拒绝不同目标或不兼容重试后，原 payload、stage 和可查询结果逐字节不变。

**三、架构、性能和文档的变化**

架构方向比上一版更清楚：HTTP 拆出了项目、传输、发布、分发、任务和存储适配器；服务上下文按实例复用；CLI 和 HTTP 复用应用服务；任务状态有枚举与生成契约；公共下载与桌面网络均增加了边界。新增大量失败场景测试也有价值，应保留这些改进。

当前薄弱点转移到了组件之间的配合。F1 是新协议经过旧白名单时被截断；F3 是持久任务在多进程下缺少清晰的执行者身份；F2、F4 是恢复与清理没有完全区分“原始有效数据”和“本次临时副本”。下一步应围绕这些约束收口，让一个流程从所有入口进入时都保持同样的含义。

性能方面，[实施线程的三轮记录](D:/Desktop/DreamingFish-Updater/docs/reviews/2026-10-18-performance-results.md)明确披露了收益和代价：目录聚合、列表和状态查询改善，ADD 导入后额外管理存储从约 16 MiB 降至约 1.5 KiB；首次发布中位耗时从约 85 秒变为约 100 秒，导入和桌面启动也没有全部提速。本轮没有重新执行这组完整三轮性能对照，所以这里引用的是交付证据，不冒充新的性能测量，也不把它与不同运行条件下旧审查的绝对耗时直接比较。

本轮独立构建确认管理网页已不再输出原来两份约 8.58 MB 的中文字体，改用系统回退；玩家前端构建仍输出约 4.40 MB 的粗体字体。因此“中文字体已优化”应明确适用到哪一端，不能理解成所有前端字体都已消失。桌面完整内存仍不能用 Rust 外壳或 Java 堆预算代表。

文档新增了 [能力矩阵](D:/Desktop/DreamingFish-Updater/docs/CAPABILITIES.md)、[存储说明](D:/Desktop/DreamingFish-Updater/docs/STORAGE.md)，ADR 也记录了静态分发与持久导入。这比之前的零散承诺更准确。当前需要继续对齐两点：能力矩阵把桌面后台任务等同于新网页，但 F1 尚未成立；任务说明把非终态转换限定为“服务重启后”，实际普通第二进程读取就会触发 F3。

备份文档现在明确只保证发布能力，列出 source-imports、source-transactions、运行设置、账号与标准源目录等需要另外保存的内容，这部分表述比此前清楚。官网已准备补丁、未上线，CI 工作流已新增、未触发远端 runner，安装器／自更新和 RTSS 仍有独立验收边界，实施记录对此作了披露，不能把它们算成已完成线上交付。

两份当前锁文件经本轮官方 npm registry 审计均为 0。Rust 上游剩余项仍见[依赖记录](D:/Desktop/DreamingFish-Updater/docs/reviews/2026-10-18-dependency-remediation.md)；本轮未独立重扫全部 Rust／Java 公告数据库，不能据 npm 归零宣布所有语言、平台和系统运行时零风险。

**五、建议的后续处理顺序**

1. 先修 F1，补完整桌面任务链路测试，并处理同步成功响应的前端状态。至少验证“检查一次 → 完成 → 任务结束 → 可以切项目”和“响应丢失 → 按同一 ID 查询”。
2. 修 F2，把事务专用的未完成 scratch 纳入恢复设计；补复制内部失败测试，保留对人工内容改动的保护。
3. 修 F3，让任务查询保持只读，只有确认执行者失效才做中断恢复；用实际服务与独立 CLI 同时访问验收。
4. 修 F4，让失败清理只删除本次新建且拥有的数据，增加冲突请求保留原件的断言。
5. 更新 R7／R12、任务能力与验收状态；重跑受影响测试和真实桌面工作流后，再形成新的候选交付。安装器、官网发布及上游依赖的剩余项继续单独跟踪。
