# 0.2.0 体积与管理体验检查

检查日期：2026-10-03。此次检查发行包、Java/Tauri 源码、真实编号式 CLI 菜单与参数帮助，并在隔离项目中实测管理网页。未修改正式程序、远程项目或真实玩家实例。所有体积使用 MiB（1024² 字节），不包含整合包、管理数据或玩家缓存。

## 实际体积

| 组件 | ZIP | 解压后 |
| --- | ---: | ---: |
| Windows 玩家发行包 | 29.6 MiB | 62.0 MiB |
| Windows 管理发行包 | 40.6 MiB | 78.5 MiB |

玩家包：私有 Java runtime 42.7 MiB、Tauri EXE 11.8 MiB、Java sidecar 3.4 MiB、Bootstrap 4.1 MiB。管理包：Java runtime 53.4 MiB、平台裁剪后 JAR 20.6 MiB、Bootstrap 4.1 MiB、启动器约 0.45 MiB。

开发构建的通用管理 JAR 为 33.5 MiB，包含多平台 SQLite 原生库；它与 Windows 发行包中 20.6 MiB 的平台裁剪 JAR 不同。当前服务器部署使用通用 JAR，可以沿用现有平台裁剪方法生成 Linux x64 专用 JAR。不能把管理 `data` 目录或 Maven/Rust 构建缓存算成程序体积。

Tauri 玩家 EXE 已包含网页资源；当前完整中文 WOFF2 字体单独为 4.2 MiB。玩家端已经是 Tauri + Vue + Java sidecar，没有必要再给玩家窗口套一层。

运行时压缩试验使用同一 JDK 21、同一模块集合、同样剥离调试信息并删除开发文件。将 jlink 模块压缩为 zip-6 后，玩家 runtime 从 42.7 MiB 降为 28.8 MiB，减少 13.9 MiB。这只是隔离试验，未用于正式包；需复测启动时间、下载和恢复流程，ZIP 下载体积也不能按相同比例推算。

## Tauri 管理桌面端的体积与架构

推荐复用管理网页和同一 Java 应用服务，Tauri 负责窗口、选择本机文件、连接配置与上传进度。共享核心已有业务规则，避免为第三个入口重写签名、发布、持久移除和恢复逻辑。

本地完整管理模式仍需要现有 Java 核心及 runtime，只增加桌面外壳；参考现有玩家 EXE 11.8 MiB，新增壳体的具体大小要实际构建才能确定。将包袱归因于 Tauri 不符合本次测量，最大部分是 Java runtime。

远程管理模式可以仅发布 Tauri 客户端，Java 核心、数据库与签名密钥留在服务器。客户端通过已认证连接或 SSH 隧道访问现有管理接口；这种模式无需在桌面包里带完整服务器运行时。应明确显示连接名称、地址、当前项目，以及“本机文件”和“服务器目录”的不同。

Tauri 使用操作系统 WebView。Windows 安装包可采用系统 WebView2 或下载引导程序；若打包离线 WebView2 安装器或固定运行时，官方文档给出的额外大小约为 127 MB 或 180 MB。当前便携包没有包含 WebView2，也不等于一台完全离线的新电脑一定具备所需组件。

参考：[Tauri 架构](https://v2.tauri.app/concept/architecture/)、[Windows WebView2 安装选项](https://v2.tauri.app/distribute/windows-installer/#webview2-installation-options)。

## 功能覆盖

“命令行”应区分编号式交互菜单与参数式 CLI，当前三个入口不完全等价。

| 功能 | Web | 编号式菜单 | 参数式 CLI |
| --- | --- | --- | --- |
| 项目创建、设置、检查发布 | 有 | 有 | 有 |
| 文件维护方式、可选内容、问题处理 | 有完整入口 | 无编辑入口，提示改用 Web 或 policy 命令 | 有 policy 命令 |
| 托管源文件操作 | 上传、浏览服务器、批量移除 | 无文件管理入口 | 单文件导入与移除 |
| 发布历史与回滚 | 查看并回滚 | 查看历史，无回滚入口 | 有 rollback 命令 |
| 玩家程序发布、生成部署包、制作实例 | 有 | 有 | 有 |
| 配色、封面、页面/新闻、音乐 | 较完整，含可视预览 | 部分，支持页面/新闻与基础配色封面，保留音乐但不能编辑曲目 | 部分，支持基础品牌配置和封面 |
| 静态分发 | 导出及 WebDAV/S3 上传 | 导出 | 导出，无直接上传命令 |
| 加密管理备份与恢复 | 无 | 无 | 有 backup create/restore |

主要依据：`InteractiveConsole.mainMenu` 和真实菜单输出、`ProjectCommand`/`ProjectPolicyCommand`/`ProjectFilesCommand`/`ProjectStaticExportCommand`、Web 的对应表单与 `AdminWebServer` 的 WebDAV/S3 上传分支。底层调用服务相同，并不代表各入口都已经暴露同样的能力。

## 实测步骤与发现

### 1. 管理内容：基本清晰

三种方式有短说明、文件夹继承和批量操作，方向合理。默认页仍同时展开可选内容与维护历史，信息量较大；辅助文字偏小，缩放和对比度需要额外验证。

![01 管理内容](D:/Desktop/DreamingFish-Updater/target/interface-audit/01-content.jpg)

### 2. 历史移除：日常负担明显

仅删除八个普通资源，页面就生成八张常驻红色“持续移除”卡片，并放在“问题处理”下。规则必须保留，但不必在日常页面全部展开。建议折叠为“已移除文件（8）”，普通退场与真正故障处理分别显示；把资源移除的“撤销”改为具体动作“允许玩家再次使用”。

![02 持续移除列表](D:/Desktop/DreamingFish-Updater/target/interface-audit/02-removals.jpg)

### 3. 检查并发布：可用，默认流程可简化

检查完成后的数量、下载量与历史入口清晰；无变更时仍展示完整发布表单。最低玩家版本由程序自动提高，却仍以普通必填项显示。建议未检查时明确禁用发布，零变更时提供“仅发布更新说明”，按当前规则和已发布玩家程序自动确定最低版本，手动提高要求放入高级选项；保留最终影响确认与过期预览保护。

![03 检查并发布](D:/Desktop/DreamingFish-Updater/target/interface-audit/03-publish.jpg)

### 4. 玩家程序发布：远程维护门槛高

表单明确要求服务器上的解压根目录，不支持直接选择本机 ZIP。服主必须先 SCP/上传并解压，再填写目录；桌面壳可以统一为拖入 ZIP → 上传/解包 → 识别版本和平台 → 显示将推广的版本 → 发布。Bootstrap 最低版本等专业参数自动识别并折叠。

历史说明写“最高版本用于新部署包”，但实际服务根据 latest 指针选择；本次 0.3.0 → 0.2.0 的编号修正说明两者并不总相同。建议明确显示“当前推广版本”“历史版本”，拒绝普通降版，并为特殊编号纠正提供单独流程及已有客户端修正包。

![04 玩家程序发布](D:/Desktop/DreamingFish-Updater/target/interface-audit/04-player-program.jpg)

### 5. 玩家实例：有推荐路径，仍有概念门槛

已经区分推荐首次部署包和高级直接制作实例，属于优点。两套表单都默认展开，平台和目录解释占用较多空间。“生成首次部署包”建议改为“生成玩家接入包”，先询问新实例还是已有整合包，再只呈现对应步骤；高级服务器输出目录、直接修改实例放入展开区。

## 优先顺序

1. 固定共享操作定义，补齐编号式菜单的重要入口，并统一术语、默认值与错误说明；如需脚本上传和个性化页面配置，再补参数式 CLI 对应命令。
2. 折叠普通移除历史，增加当前推广版本标识，并自动填写兼容版本和平台等信息。
3. 为远程程序发布增加本机 ZIP 上传；让添加文件、检查、确认、发布形成连续的日常路径。
4. 做轻量 Tauri 管理壳，复用已有网页与核心，分别支持本地管理和远程连接。
5. 单独验证 jlink 压缩、字体方案及平台原生库裁剪；之后根据数据决定是否值得把某些 Java 能力逐步搬到 Rust。

访问范围和限制：网页实测采用同版本隔离项目，未触碰正式项目或公开发布；CLI 实际运行菜单和帮助，并检查处理代码，未逐项执行所有写操作。没有执行真实 Minecraft 启动、全键盘/屏幕阅读器评估、全部分发平台上传或桌面管理端构建，因此不作完整无障碍与最终桌面增量体积承诺。
