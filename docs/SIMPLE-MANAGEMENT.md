# 简化文件维护说明

0.2.0 保留普通同步和强制同步，增加真正的首次提供。日常方式、文件退出维护和历史问题处理各有明确入口，服主不需要配置规则优先级。

新版管理界面的目录浏览、上传清单、逐项重试、归档恢复与部署流程见 [管理端工作区](ADMIN-WORKSPACE.md)。三种维护方式和玩家端语义保持一致。

| 日常方式 | 行为 | 玩家操作 |
| --- | --- | --- |
| 普通同步 | 缺失补齐、跟随更新，替换玩家修改前备份 | 停用或自行管理 |
| 强制同步 | 始终与发布一致；文件夹同时归档额外文件 | 不能豁免 |
| 首次提供 | 已有保留、缺失提供一次；之后不覆盖、不补回 | 自己维护或主动恢复默认 |

旧默认配置不再作为第四种新设置。选择首次提供后，老玩家不会自动获得后来修改的模板；新玩家取得当前模板，需要时老玩家可以主动恢复默认或由服主发布修复。旧签名发布中的默认配置仍按原行为执行。

## 移除只问副本是否留给玩家

**移除玩家副本**：默认选择。原副本先备份再移出，包括首次提供、停用和自行管理的副本；规则持续有效，后来装回仍会处理。

**停止维护，留给玩家**：停止下发和日常维护，玩家保留或自己添加副本。强制目录不允许留下额外文件，需要先把目录改为普通同步。

重新提供同一资源会结束普通持续移除。结束一条移除要求也会交还历史副本，旧包直接更新时不会被基线差异再次删除。历史问题版本的处理独立保留，不能通过回滚内容或重新提供其他版本无意取消。

## 历史问题使用一个入口

在“管理内容 → 历史文件与问题处理 → 按发布版本管理”选择整合包发布版本，查看它当时提供过的文件，点击“处理这个版本”。也可以直接使用“处理问题文件”，按整合包发布筛选后勾选具体坏版本。需要替换时先上传正确文件；所有玩家各重置一次放在更多替换选项内。

例如：1.0 曾经提供 B 1.0，后来选择“停止维护，留给玩家”。之后发现 B 1.0 会导致崩溃，仍可从历史发布里选中它，保存“移出问题版本”，再检查并发布。玩家已豁免、停用或改名的匹配副本也会先备份再移出；正常 B 2.0 保持其原维护方式。

普通删除生成的持续移除要求保留在后台，不再逐条显示为问题卡片。历史窗口会标明“已移除（自动处理）”，在该文件的“移除要求”中可明确结束要求、允许玩家保留；这一变化也需要发布后生效，强制目录仍按目录规则处理。文件历史按确实出现过的发布列出，删除后重新加入的文件不会被误算进中间版本。

当前仍在源目录的同一坏版本可以直接准备移出并发布一次，不要求先发布删除版本再发布撤回。已上传的新替代内容不会被旧版本选择误删。

匹配的活动或停用副本进入带原因的备份。玩家可以查看备份，但仍匹配有效移除或问题要求的内容不能直接恢复到游戏。已知坏版按内容指纹识别，模组还使用 ID 与版本，因此相同版本的改包也可能被处理；普通持续移除覆盖同一模组的其他版本。

## 不同加入时间使用同一目标

| 情况 | 最新 5.0 持续移除 D 后 |
| --- | --- |
| 下载 4.0 完整包，首次在 5.0 加入 | D 备份移出 |
| 2.0 直接更新到 5.0 | D 备份移出 |
| 3.0 已移除，4.0 重新提供，5.0 再移除 | 4.0 允许 D，5.0 的新移除要求生效 |
| 玩家已豁免、停用或改名 | 对应副本仍被处理 |
| 5.0 后又把 D 装回 | 下次检查再次备份移出 |
| 有效的新模组使用以前 D 的文件名 | 不仅凭同名把它当作 D |

新目标明确携带持续要求，不依据玩家是否经过某个中间版本推断删除。正式下载包仍需正确的项目绑定与签名基线；不支持新规则的玩家端必须先升级。

尚未取得的新发布不能在离线时获知。已有游戏进程不会自动卸载模组；本次启动检查完成取得的目标后才授予许可。

## 升级和兼容

发布新规则前先提供 0.2.0 玩家端程序。旧项目首次检查会迁移实际历史删除，预览和处理卡展示待发布要求，可以结束后再检查；迁移不会因重复检查撤销玩家保留的决定。

旧签名发布保留原始字节和原语义。采用新规则后不能用旧管理端向同一项目发布降级目标。首次格式升级后，旧玩家程序遇到不支持的偏好或恢复事务会明确失败；应重新运行支持该格式的程序恢复。

管理端程序、玩家端程序与整合包内容各自发布，调整维护规则后仍需确认发布整合包。Java 集成测试使用隔离的模拟模组和 HTTP 服务，不能替代实际 Minecraft 启动器、模组依赖及生产分发验收。
