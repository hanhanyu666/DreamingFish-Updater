# [玩家 - 0.3.3][管理 - 0.3.2] 一键发布官方玩家端，新增整合包外层目录与配置合并

**本次玩家端和管理端都要更新。服主需要把玩家端程序 0.3.3 发布给玩家：升级到管理端 0.3.2 后，在“发放 → 玩家端程序”点“检查官方新版”再点“发布给玩家”即可，也可以手动上传 ZIP。外层目录和配置合并要求玩家端 0.3.3。仅升级远程管理服务不会替换服主电脑上的旧桌面程序，桌面版需要另外升级。**

管理端与桌面版升级为 **0.3.2**，玩家端升级为 **0.3.3**，Bootstrap Agent 保持 **0.1.2**。这一版主要做了三件事：

- 玩家端程序不用再手动下载、上传，可以一键或自动发布官方新版；
- 启动器旁的教程、背景图等整合包外层文件也能随更新下发；
- 启动器配置可以只改指定的字段。

网页管理端也改用和桌面版相同的工作区。

## 主要更新

### 一键发布官方玩家端

- **检查官方新版**：在“发放 → 玩家端程序”点“检查官方新版”，显示官方最新的版本、大小和更新说明，以及它要求的最低管理端和 Agent 版本。
- **发布给玩家**：点击后，管理服务从 GitHub 下载官方程序，核对官方签名和每个文件，再用本项目签名发布。不用自己下载 ZIP 再上传。已有玩家下次启动时自动升级，服务器首页、公告、背景、音乐和玩家本地设置都保留。
- **自动发布**：可以打开“官方发布新版后自动发布给玩家”。管理服务每小时检查一次，有更新版本时自动完成同样的下载、核对和发布。默认关闭。
- **暂停玩家端升级**：点卡片上的“暂停玩家端升级”后，玩家继续使用当前程序，旧版玩家端的程序更新入口也一起关闭。暂停期间不会自动发布，也不会自动恢复。
- **国内服务器也能下载**：先通过 GitHub API 下载，打不开 `github.com` 的服务器只要能访问 `api.github.com` 就能取得官方程序；API 不通时再直连 `github.com`。
- **下载进度与续传**：卡片上显示进度条。断线或停滞后会从已下载的位置继续，15 分钟完全没有数据或总计超过 6 小时才放弃。下载期间可以继续使用管理端、切换项目，关闭或刷新页面后回来仍显示进度；不想等了可以点“终止下载”，不会发布任何内容。
- **支持代理**：管理服务设置了 `HTTPS_PROXY` 环境变量，或 Windows 开着系统代理时，从 GitHub 下载会走代理。代理只用于下载官方玩家端，上传到 OSS、WebDAV 仍按原来的方式连接。
- 服务器没有代理、下载太慢时，也可以在自己电脑上下载 ZIP，展开“手动上传玩家端发行 ZIP”发布，效果相同。

### 整合包外层目录

- **外层文件也能更新**：启动器旁的进服教程、启动器背景等文件，可以和模组一起维护。在“文件”页点“外层目录”，在示意文件树里点选整合包所在的层级（或选择从游戏实例向上 1 至 8 级），启用后导入要维护的文件，再检查并发布。
- **不需要重新分发整合包**：外层目录的设置随发布一起签名下发，已有玩家（玩家端 0.3.3 起）下次启动时自动启用，不用替换文件或重新制作部署包。
- **先核对再写入**：玩家端会核对本机的目录结构，对不上时只跳过外层文件，模组和配置照常更新，并在日志里写明原因；玩家把目录整理好后，下次启动自动补上。目录落在桌面、文档、用户目录或磁盘根目录等过宽位置，或属于其他项目时，同样只跳过外层文件。
- 只更新服主明确导入的文件，不接管 `.minecraft`、其他游戏实例、存档、截图和账户文件。多个实例共用一个外层目录时共享更新锁，另一个实例正在运行时不提交外层文件的修改。

### 启动器配置合并

- 在“文件”页“导入文件”旁的下拉菜单选择“配置合并规则（高级）”，可以只修改 JSON、INI 文件里的指定字段，或在 Minecraft 版本 JSON 里追加 JVM 参数。
- 没有指定的字段保留玩家自己的设置，合并前备份原文件。账户、个人内存等设置不允许合并。

### 外部托管（OSS / WebDAV）

- **保存密钥**：可以勾选“保存密钥”，上传成功后密钥保存在管理服务的数据目录，网页上不再显示。临时会话令牌不能保存。
- **发布后自动上传**：保存密钥并开启后，发布整合包、发布或暂停玩家端程序、自动发布、修改玩家端首页之后都会自动上传到 OSS / WebDAV。内容没变不上传，失败原因显示在页面上。
- 新增目录选择、阿里云 OSS 地址填写提示和填写历史（只记录 Access Key ID 等非秘密内容），并修正服务器文件选择器的图标布局。
- 暂停玩家端升级后上传时，会清理本项目停用的程序入口，并检查这些地址已经返回 404。

### 管理端与桌面版

- **网页管理端改用新工作区**：和桌面版使用同一套界面，移除了旧页面和切换按钮。旧网址会自动跳转到对应的项目和页面，原有数据和管理 API 不变。
- 外层目录和配置合并都放在“文件”页，示意文件树标出游戏实例和更新根目录。
- 修复“玩家端设计”导入和导出展示内容时的复制错误，编辑的内容可以正常校验、导出和回填。
- “历史问题文件”明确提示需要要求玩家删除的文件。
- 部署说明改用通用的 Agent 参数写法：在版本 JSON 的 `arguments.jvm` 里加入相对路径的 `-javaagent`，换启动器也不用重新填写；PCL 专用的 `{verpath}` 写法作为备选另外说明。已经部署好的实例不需要修改。

### 玩家端 0.3.3

- 支持整合包外层目录和配置合并。
- 程序升级更稳妥：从实际安装的 Agent 读取版本，新程序需要更新的 Agent 时保留当前程序，并提示服主重新制作实例；新版本启动失败、退回旧版本后，会记住这个版本，不再每次启动都重复切换。
- 服主暂停玩家端升级时，玩家端照常检查整合包，并在日志里说明原因。
- 修复展示内容复制时可能报错的问题。

## 更新教程

### 升级前备份

1. 等导入、发布、部署包下载和官方玩家端下载完成后再升级，或者先点“终止下载”。关闭窗口通常只是隐藏到托盘；要替换程序文件时，用连接页的“退出桌面端”或托盘菜单退出，让旧进程真正结束。
2. 桌面用户先在连接页点击“数据目录”，确认实际保存位置；自己选过管理目录的，另外备份那个目录。终端用户备份实际的管理端目录。要保留 `data/`、`management-settings.json`、`management-web-auth.json`（注册过账户时），以及桌面连接、日志和恢复记录；项目签名身份必须保留。
3. 外部的标准整合包目录和外部管理目录也要单独备份。加密“发布数据备份”不能代替上面的完整备份。不要用新包里的空目录覆盖已有数据，也不要把管理数据或签名私钥发给玩家。

### Windows 桌面安装版

1. 在桌面连接页点击底部的版本号“检查更新”，有新版本时选择“立即更新”，按提示关闭工作区并安装。更新完成后程序会自动重新打开。
2. 也可以下载 `dfs-admin-desktop-windows-x64-0.3.2-setup.exe`，完整退出旧桌面程序后运行安装包，沿用原来的安装位置。保留原有数据，不要选择删除或重置管理数据。
3. 打开原来的连接，确认连接页显示 **0.3.2**，原项目、账户和发布历史都在。桌面自带的本机管理核心会随程序一起更新；单独部署在服务器上的终端管理端，要按下面的终端步骤另外升级。

### Windows 桌面便携版

1. 下载 `dfs-admin-desktop-windows-x64-0.3.2.zip`，完整解压到一个固定目录。不要直接在压缩包里运行，也不要只复制里面的 EXE。
2. 完整退出旧桌面程序并做好备份后，用新版的程序文件、`core/` 等程序资源替换旧程序；保留旧目录里已有的 `data/`，不要用新包里的空数据覆盖它。
3. 如果搬到新目录，要连同原来的 `data/` 一起搬；原来放在外部的管理目录和整合包目录仍要保留，必要时重新定位连接。运行 `DreamingFishAdminDesktop.exe`，确认版本和原有项目都正确。

### Windows / Linux 终端管理端

1. 下载对应系统的 `dfs-admin-windows-x64-0.3.2.zip` 或 `dfs-admin-linux-x64-0.3.2.zip`。先按原来的方式（终端、systemd、Docker 或启动脚本）停止管理端进程；如果网页管理和公共下载服务是分开运行的，两个都要停。不要在旧进程还在运行时混用新旧程序文件。
2. 解压新包，替换原目录里的程序、`app/`、`runtime/`、`support/` 和对应的启动脚本；保留 `data/`、`management-settings.json`、`management-web-auth.json`、恢复材料和外部标准整合包目录。继续使用原来的服务参数、端口和反向代理配置。
3. 按原来的方式启动。在管理端目录检查版本：Windows 运行 `.\DreamingFishAdmin.exe --version`，Linux 运行 `./dfs-admin --version`，确认输出 **0.3.2**。Linux 上如果解压工具没有保留执行权限，给 `dfs-admin` 和 `runtime/bin/java` 补上执行权限。
4. 重新打开或刷新管理网页，确认原账户、项目和发布历史都在。网页会直接进入新工作区，旧网址会自动跳转。使用单独公共下载服务的，按原来的部署方式恢复服务，并检查玩家更新地址能访问。
5. 服务器访问 GitHub 需要代理时，可以在启动网页管理前设置环境变量，例如 Linux 上 `HTTPS_PROXY=http://127.0.0.1:7890 ./dfs-admin web`。不设置也能使用，只是下载官方玩家端可能较慢。

### 玩家端是否需要更新

1. **本次需要发布新的玩家端程序 0.3.3。** 先把管理端升级到 0.3.2，再进入“发放 → 玩家端程序”，点击“检查官方新版”，看到 0.3.3 后点“发布给玩家”并确认。管理服务会自己从 GitHub 下载约 37 MB 并核对签名；国内服务器没有代理时可能要一两个小时，期间可以离开页面，回来仍显示进度。
2. 也可以手动发布：下载 `dreamingfish-player-windows-x64-0.3.3.zip`，在同一张卡片展开“手动上传玩家端发行 ZIP”，上传后点“检查发行包”，确认识别出的版本是 0.3.3、平台是 windows-x64，再点“批准并发布”。两种方式效果相同，已经发布过的版本号不能重复发布。
3. 使用 OSS、WebDAV 等外部托管的，发布后要重新“导出并上传”，玩家才能读到新程序。也可以在“外部托管”勾选“保存密钥”并开启“发布后自动上传”，以后发布会自动上传。
4. 发布后，已有玩家下次联网打开更新器时，会自动下载新程序并重新启动，不需要重新安装，也不需要重新制作或发放整合包。原来的标题、配色、页面和公告都保留。Bootstrap Agent 仍为 0.1.2。
5. 想使用外层目录或配置合并，先确认玩家端 0.3.3 已经发布，再到“文件”页启用；发布整合包时管理端也会检查这一点。“官方发布新版后自动发布给玩家”默认关闭，需要时在卡片上打开。
6. 已经部署好的实例不需要修改 Agent 参数。只有首次发放或制作新的完整整合包快照时，才需要生成薄部署 ZIP；普通的在线模组和配置更新继续走检查、发布流程。

### 升级后检查

1. 确认实际使用的管理端和桌面程序都是 **0.3.2**，原项目、账户、签名身份和发布历史完整。如果显示空项目或新建账户向导，先核对连接和数据路径，不要直接重新建库或删除恢复记录。
2. 在“发放 → 玩家端程序”点击“检查官方新版”，应能看到官方版本 0.3.3；发布完成后卡片显示当前玩家端为 **0.3.3**，再检查会提示已是官方最新。
3. 用测试实例打开一次更新器，确认它自动升级到 0.3.3，首页和公告保持原样，整合包能正常完成一次更新。启用了外层目录的，确认外层文件已更新，玩家端日志里没有“整合包外层文件暂未更新”的提示。
4. 检查公共下载服务和项目的玩家更新地址；使用外部托管的，确认上传状态正常。签名、整合包维护规则和最低玩家端版本不需要因本次升级调整。
